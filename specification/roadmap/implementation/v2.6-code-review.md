## 1. 🔴 HIGH — the next touch after a carousel is classified against a press that ended long ago

**Where:** `firmware/src/main.cpp` — `serviceTouch`, the early return when `carousel.isOpen()`, and
`firmware/src/pure/touch.h`'s `TouchGestures` state.

**Failure scenario.**

1. A silent hold passes 1.2 s. `TouchGestures` reports `kHeldSilent` — with the finger **still
   down**, so its own `held_` is true and `reported_hold_` is true.
2. `onTouchGesture` opens the carousel.
3. From the next loop onward `serviceTouch` returns early: *"while the carousel is open the finger
   belongs to it, and to nothing else."* Correct as a rule, and it means `TouchGestures` **never
   sees the release**.
4. The person chooses a face and lifts their finger. The carousel closes. `TouchGestures` still
   believes a finger is down at the coordinates where the hold began.
5. They tap the face. `sample.down && !held_` is false, so the press is not re-captured — no new
   `start_x_`, no new `zone_`. Execution falls into the *held* branch, measures the distance from
   the **old** start, and if that exceeds 40 px reports a **stroke that nobody performed**, in
   whatever zone the carousel gesture began in.

So the first touch after every carousel use is misclassified, and the character reacts to a caress
it was not given — plus an `event{touch, stroke}` on the wire, which may draw a spoken reaction.

**This is the third instance of one shape.** v2.4: the mute gesture leaked into affection. v2.5: the
mono observer ran before the stereo one, so the VAD used the previous frame's confidence. Here: a
second consumer takes the finger and the first is never told. Each time the individual rule was
right and the *handoff* was wrong.

**Why the tests did not catch it.** Every `TouchGestures` test drives it directly with a complete
press-and-release. Nothing models a consumer stealing the finger mid-press, because until this phase
no consumer did.

**Proposed fix.** `TouchGestures::forget()` — end the press *and* the run, distinct from `reset()`,
which v2.4 deliberately narrowed to the run alone. Two methods because they answer two questions:
`reset()` is "the state changed, so the count is no longer meaningful", and `forget()` is "someone
else has the finger". Call it when the carousel opens.

**Regression test.** Open a carousel mid-press, forget, release, then a fresh tap on a different
zone reports `kTap` in *that* zone with `count == 1`.

## 2. 🔴 HIGH — the carousel abandons itself, via the turn its own opening created

**Where:** `firmware/src/main.cpp` — `onTouchGesture`'s `endListening("carousel")`, and `apply()`'s
`carousel.abandon()`.

**Failure scenario.**

1. The hold opened a listening window at 0 ms. At 1.2 s it converts, and the carousel closes the
   window — correctly, since *"a microphone left open by a gesture that was reinterpreted is a
   microphone nobody knows is on"*.
2. But `listen_stop` does not discard anything. The server has 1.2 s of audio — a breath, a chair,
   a fragment of a word — and runs the ordinary turn on it: recognition, then a model call, then a
   reply.
3. A second or two later `reply` arrives. `apply(kReplyStarted)` runs, and `apply` calls
   `carousel.abandon()`.
4. **The strip vanishes from under the person's finger**, the previewed face reverts, and the device
   starts talking about whatever it thought it heard.

The abandon call is right in intent — a face chosen by an interrupted gesture is a face nobody
chose. What is wrong is that it cannot tell a state change *caused by the carousel itself* from one
that genuinely invalidates it.

**Why the tests did not catch it.** `abandon()` is unit-tested and behaves exactly as specified. The
defect is that it is *called* in a case its specification did not consider, which no test of
`abandon()` can see — the same shape as v2.5's finding #2, where a function was correct and had no
callers, inverted.

**Proposed fix.** Abandon only when the finger has already left the glass. If it is still down the
person is still choosing, and the device changing state behind them is not a reason to take the
carousel away — the whole point of the strip is that it is the only thing that owns the finger while
it is open.

**Regression test.** Not expressible in `pure/` alone: this is glue. What *is* pure and worth
pinning is the rule — a carousel that is abandoned while the finger is down keeps its preview — so
the test goes on the guard's condition rather than on `Carousel`.

## 3. 🟡 LOW — one skin change that does not go through the loader

**Where:** `firmware/src/main.cpp` — `apply()`'s abandon path calls
`renderer.setSkin(roboface::skinAt(...))` directly, while every other skin change goes through
`wearSkin` → `loadSkin`.

**Why it is real.** RF-083's whole argument is that the fallback is the ordinary path rather than an
exceptional one. One call site bypassing it is one call site where a broken manifest produces
`setSkin`'s silent refusal instead of a named reason — and `setSkin` refusing means the face stays
whatever it was, which after an abandon is the *preview*: the opposite of what abandoning is for.

**Why it is deferred rather than fixed now.** Finding #2 removes this call site entirely — the
abandon moves behind a guard and stops running during a state change with the finger down. Fixing
both would mean writing the same line twice. If #2's fix leaves it standing, it comes back here.

**Home:** re-check after finding #2 lands.

# Fixes applied

**Final validation:** `pytest` 740 passed / 3 skipped · `mypy --strict` clean · `ruff` clean ·
`pio test -e native` 484 passed · `pio run -e cores3` compiles and flashes.

## #1 — `TouchGestures::forget()`

**The change.** A second method, deliberately not a flag on `reset()`. v2.4 narrowed `reset()` to
the tap *run* on purpose — a press that spans a state change must survive — and this is the opposite
case: a press another consumer has taken must not. `reported_hold_` is set rather than cleared, so
whatever the press was becoming, it does not become it after the handoff either.

**The regression test.** A hold long enough to be the carousel's, in one corner; `forget()`; then a
tap on the cheek. It must be a `kTap` in `kCheek` with `count == 1` — not a stroke measured from the
corner. Plus a test holding `forget` and `reset` side by side, because the reason there are two is
the whole content of both.

**Architecture impact.** None to a contract, but a rule worth recording: **`pure/` classes that hold
a press need a way to be told they have lost it.** This project now has three consumers of one
finger (PTT, gestures, carousel) and the last three phases have each produced one defect at a
handoff between two of them. The individual rules keep being right.

## #2 — abandon only once the finger has gone

**The change.** `apply()`'s abandon is guarded on `!was_pressed`. While the finger is down the
person is still choosing, and the device changing state behind them is not a reason to stop them —
particularly when the state change is one the carousel itself caused by closing the listening
window its own gesture opened.

**No pure regression test, and that is the finding rather than an omission.** `Carousel::abandon()`
is unit-tested and behaves exactly as specified; the defect was that it was *called* in a case its
specification never considered. Nothing inside `Carousel` can see that, and a test that mocked
`apply()` would be testing the mock. The manual document carries the on-device check: open the
carousel, hold it, and let the device reply — the strip must stay.

**Architecture impact.** DEVICE_UI already says the strip owns the finger while it is open. This
makes that true against the device's own state machine as well as against the gesture classifier.

## #3 — removed rather than fixed

Finding #2's guard replaced the direct `setSkin` call with `wearSkin`, which goes through
`loadSkin`. The bypass no longer exists, so there is nothing left to defer.
