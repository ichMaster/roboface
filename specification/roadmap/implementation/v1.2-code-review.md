## 1. 🟠 MEDIUM — a dropped socket leaves the utterance buffer allocated

**Anchor:** `server/roboface_server/router.py` — `serve`'s cleanup, versus `_end_utterance`.

**Failure scenario.** The connection cleanup calls `responder.forget(session_id)` — that was v0.1's
fix for exactly this shape — but nothing calls `_end_utterance`. A device that drops mid-utterance
therefore leaves up to `MAX_UTTERANCE_BYTES` (960 KB) held in `conn.utterance` until the
`Connection` is collected. One device on a flaky link, reconnecting repeatedly mid-sentence, is the
case that turns this from untidy into a memory profile that climbs.

The cap makes each instance bounded, which is why this is MEDIUM rather than HIGH — but the cap
exists to bound a *live* utterance, not to bound how many dead ones may accumulate.

**Fix.** Release the utterance in the same `finally` that forgets the session. One place already
ends a window for the four reasons an utterance can end; a disconnect is the fifth and belongs there.

---

## 2. 🟠 MEDIUM — the device can keep capturing into a window the server has closed

**Anchor:** `firmware/src/main.cpp` — the `kError` branch versus the PTT hold.

**Failure scenario.** The server ends a window on an oversize utterance and sends `bad_frame`. The
firmware's error branch cancels the hold — but only if the fault arrives as an `error` frame it
parses. If the window closed for any other reason while a finger is still down, the device keeps
capturing and sending binary frames, and **the server refuses each one with another `bad_frame`**:
a loop of errors for as long as the person holds, each one a round trip.

More generally, the device treats "I am holding" as sufficient authority to keep sending. It is not
— the server owns the window, and the device's copy of that state can be stale.

**Fix.** Stop capturing whenever a `bad_frame` arrives while listening, not only on the fault path.
The device's hold is a *request* for a window; the server's refusal ends it.

## 3. 🟡 LOW — `/loopback` playback is unverified

Capture is verified (30–70% peak on speech) and the product's playback path is verified separately
(TTS is audible), so both halves are independently known good; what is unconfirmed is the
diagnostic's own replay. It sends nothing to the server and sits on no product path. Recorded in the
execution report rather than left implied. **DEFER — documented.**

## 4. 🟡 LOW — `MIC_GAIN` is board-specific with no runtime check

64 is right for this Core S3's ES7210 and was found by measurement, not from a datasheet. Nothing
checks it at runtime, so a board that needs a different value presents as poor recognition rather
than as a gain problem — the exact confusion this phase already paid for once. A boot-time check
(capture a frame, warn if the noise floor is implausibly low) would catch it, but it belongs with
v1.3's recognition where the symptom would otherwise surface. **DEFER → v1.3.**

## What's solid

- **The window's rules are pinned where they belong.** `device_binary_meaning` was written in v0.1
  and consumed unchanged; the router moves a phase rather than special-casing a frame, which is what
  v0.1's comment on `_handle_binary` predicted it would.
- **The cap is in bytes and checked before storing.** Seconds would have to be trusted across a
  network, and checking after storing would take the memory the cap exists to protect.
- **The digest makes "assembled intact" observable.** A byte count is satisfied by reordering and by
  duplication; the digest is not, and it is the evidence v1.3 will want when a transcript is wrong.
- **The pure/glue split held again.** Every fault this phase found was in the glue — the mic queue,
  the gain, the drain, the state transition — and every one of them was found by *measuring on the
  device*, which is what the split predicts and what the host tests are deliberately not asked to do.
