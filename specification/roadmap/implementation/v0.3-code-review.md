## Findings

### 1. 🟠 MEDIUM — The first connection attempt is aborted and immediately restarted

**Where:** [`app/ws.cpp`](../../../firmware/src/app/ws.cpp) — `begin()` ends with `connect()`;
`loop()` opens with `if (!connected_ && now_ms >= retry_at_ms_)` and `retry_at_ms_` starts at **0**.

**Failure scenario.** `begin()` opens the socket. The very next `loop()` — microseconds later —
finds `now_ms >= 0` true, calls `connect()` again, and `WebSocketsClient::begin()` tears down the
in-flight attempt to start another. **Every boot throws away its first connection attempt**, and on
a slow or lossy network the second is no more likely to succeed than the first was.

**Seen on the board**, which is what makes this a finding rather than a reading:

```
[ws] server 192.168.1.64:8000/ws
[ws] reconnecting in 427 ms      ← before the first attempt could possibly have finished
```

**Proposed fix.** Have `begin()` set `retry_at_ms_` to the moment the first attempt should be given
up on, so the supervisor waits for it rather than racing it.

### 2. 🟠 MEDIUM — The reconnect message describes a delay that is never waited

**Where:** the same six lines. `loop()` computes `delay_ms`, sets `retry_at_ms_ = now + delay_ms`,
prints *"reconnecting in `delay_ms` ms"*, and then calls `connect()` **immediately**.

The *timing* is defensible — attempt now, wait before the next — but the message says the opposite
of what happens. **Serial is the only diagnostic channel this device has** (ROADMAP §v0.3 makes it
the debug channel and the turn source), and a person reading that log would time the reconnects,
find them instant, and go looking for a bug in the backoff — which is correct and tested.

A log that misdescribes the code is worse than no log: it costs the reader the time to disprove it.
This is the same standard the server's logging module was held to in v0.1.

**Proposed fix.** Say what happened and when the next one is due: *"attempt N failed; retrying now,
next in `delay_ms` ms"*.

### 3. 🟠 MEDIUM — The device inherited the server's frame cap, which is sized for a server

**Where:** [`pure/ws_protocol.h`](../../../firmware/src/pure/ws_protocol.h) —
`kMaxTextFrameBytes = 65536`, used both as the contract value *and* as the device's own inbound
bound in [`app/ws.cpp`](../../../firmware/src/app/ws.cpp).

**Failure scenario.** A 64 KiB text frame arrives. `parseServerFrame` hands it to ArduinoJson, which
allocates a document to parse it — on a board with **320 KB of RAM**. That single frame is a fifth of
memory before the JSON tree is built, while the audio buffers and the face framebuffer of v1–v2 are
already spoken for.

The mirror was right to copy the number as a *contract* fact — the server refuses more than 64 KiB
and the device must not send more. But it was wrong to reuse it as the *device's* limit. The two
constraints are unrelated: the server has gigabytes, and the largest text frame this device will
ever legitimately receive is a `reply` delta of a few dozen bytes. Bulk data — audio, JPEG — is
binary and never passes through this path at all.

**Proposed fix.** Keep `kMaxTextFrameBytes` as the pinned contract value, and add a separate,
much smaller `kMaxInboundFrameBytes` for what this device will accept. Keeping them distinct is
what stops the contract test and the memory budget arguing with each other.

### 4. 🟡 LOW — The client and its owner are file-scope globals — DEFER → v1.1

`ws.cpp` holds `WebSocketsClient client` and `Ws* active` at file scope, and the static event
callback dereferences `active` with no ownership rule. One device, one socket, so it is correct
today — but a second `Ws` would silently clobber the first, and the callback would attribute its
frames to whichever constructed last. The library's C-style callback is what forces this shape;
untangling it properly wants doing when v1.1 adds the audio path and the file grows.

### 5. 🟡 LOW — A `reply` outside a turn prints while the state machine rejects it — DEFER → v0.4

In `main.cpp`, a `reply` delta arriving in `idle` calls `apply(kReplyStarted)`, which the machine
correctly rejects — and then prints the text anyway and sets `reply_in_progress`. The screen (from
v0.4) and the serial log would disagree about whether a turn is happening. Not reachable today: the
server only sends `reply` in response to a `text_in`. Worth resolving in v0.4, where device state
starts driving something a person can see.

## What's solid

- **The pure/glue split is enforced, not intended.** The `native` build filter rejects an Arduino
  include in pure code, demonstrated by deliberately adding one. 61 host tests run with no board.
- **The cross-language contract test earns its place.** It reads the C++ header and compares it to
  `protocol.py` in the **Python** job, so drift is caught by someone who never runs `pio` — verified
  by drifting the header on purpose.
- **The exhaustive transition test found a real bug before hardware could** — `wifi_connecting`
  exiting on the link rather than the socket, which would have shown `idle` to a person who could
  not yet be answered.
- **Moving `parseWsUrl` into `pure/` paid immediately**, catching `:0` and `:70000` silently
  becoming a `uint16`.
- **The backoff behaves on hardware exactly as it does on the host** — 427 / 774 / 1842 / 3551 /
  6640 / 13256 ms, jittered and capped.
