# v0.3 — GitHub Issues

Issues for phase **v0.3 — Firmware skeleton: Core S3 as a WSS client** (version **v0 — Skeleton**),
derived from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§v0.3) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§Components, §Hardware map, §Contracts → WS device↔server,
§Error codes, §Device states, §Firmware architecture, §Stack and repository layout, §Testing and CI).
This file is scoped to a single phase; IDs continue from the previous phase
(RF-011 → **RF-012…RF-017**).

v0.3 is the first firmware, and the first code in this repository that is not Python. The board
becomes a client of the server v0.1 and v0.2 built: it joins WiFi, opens a WebSocket, greets with
`hello`, and turns a line typed over USB serial into a `text_in` — printing the model's reply back
out. No audio, no camera, no face; USB serial is the debug channel and the only turn source, which
is what makes a testable loop possible before any of that exists.

The **two-layer split is the point of the phase**, not a tidiness preference. ARCHITECTURE
§Firmware architecture: pure logic is header-only, `namespace roboface`, Arduino-free, and host-tested
under `pio test -e native`; glue is `namespace app` and owns the hardware. Everything that can be
wrong — frame parsing, the state machine, backoff — lives in the half a laptop can test, because the
other half can only be tested by standing at a board with a cable.

## Reconciliation with the released server

**Ground truth is `v0.2.1` (commit `1e4f082`) — the real code, not the design.** The firmware is a
client of a server that already exists and is already released, so every wire detail below is read
from `server/roboface_server/protocol.py` rather than from the specification. Six facts change what
these issues say.

| # | What the released server actually does | Consequence for the firmware |
|---|---|---|
| R1 | **It serves plain `ws://`, not `wss://`.** [`app.py`](../../../server/roboface_server/app.py) calls `uvicorn.run(...)` with no `ssl_keyfile`/`ssl_certfile`, so there is no TLS anywhere in the product today — while ROADMAP §v0.3, ARCHITECTURE §Overview and this file's own title all say "WSS". | RF-016 implements a **`ws://` client against a configurable URL**, because that is what connects to the thing that exists. The scheme lives in `config.h`, so turning TLS on later is a config change plus a CA bundle rather than a rewrite. **The drift is real and is recorded in ARCHITECTURE by RF-016** — the specification currently promises a transport the server does not offer. |
| R2 | **A reply is many frames, not one.** v0.2 changed `reply` cardinality: N deltas with `final: false`, closed by exactly one `final: true` (v0.2 review, "Architecture impact"). | RF-013 and RF-017 must **never assume one reply per turn**. The serial channel accumulates deltas and prints them as they arrive; the terminal frame ends the turn. A parser written from the v0.1-era design would drop every delta after the first. |
| R3 | **`ErrorCode` has twelve values, including `bad_frame`** (RF-009), and `internal` became reachable in the v0.2 review. | RF-013's error enum mirrors **all twelve**. The device renders whatever arrives; a code it does not know is still a fault, not a parse failure. |
| R4 | **The LLM leg produces only `llm_failed` / `llm_timeout` / `rate_limited`** — the v0.2 review deliberately stopped it emitting `unauthorized` and `server_unreachable`, because those blame the device for the server's problem. | The firmware still has to handle all twelve (a later phase's ASR/TTS legs use others), but should not special-case the LLM ones. |
| R5 | **A text frame is capped at 64 KiB** and refused *before* parsing (`MAX_TEXT_FRAME_BYTES`, v0.1 review fix 1). Binary frames carry raw payloads with **no envelope**. | RF-013 mirrors the cap so the device does not send what the server will refuse — and the device's own inbound buffer needs a bound for the same reason, on a board with 320 KB of RAM. |
| R6 | **`hello.audio_fmt` is the exact string `pcm16/16000/1`** and **`proto_ver` is `1`, with no compatibility window** — any other version is rejected with `proto_unsupported` and the socket closes. | RF-013 pins both as constants. RF-017's DoD check includes deliberately announcing a wrong version and seeing the board go to `error` rather than retry-loop. |

`tools/chat.py` is the reference client for all of this: it does in Python what RF-016 does in C++,
against the same server, and can be run side by side while debugging the board.

**Board:** PlatformIO board id `m5stack-cores3` (ESP32-S3, 16 MB flash, 8 MB PSRAM). Libraries
verified present in the registry: `m5stack/M5Unified`, `bblanchon/ArduinoJson`,
`links2004/WebSockets`.

## v0.3 — Firmware skeleton: Core S3 as a WSS client

### RF-012 — PlatformIO project: two envs, config, and a host test that runs

**Description:**
Create `firmware/` as a PlatformIO project with **both** environments from the start: `cores3` for
the board and `native` for host tests. Touches `firmware/` only. The `native` env is not an
afterthought — it is where every issue after this one is actually verified, so it exists before any
code does.

**What needs to be done:**
- `firmware/platformio.ini`:
  - `[env:cores3]` — `platform = espressif32`, `board = m5stack-cores3`, `framework = arduino`,
    PSRAM enabled (`board_build.arduino.memory_type`, `-DBOARD_HAS_PSRAM`), a sensible
    `monitor_speed`, and `lib_deps` for `m5stack/M5Unified`, `bblanchon/ArduinoJson`,
    `links2004/WebSockets`.
  - `[env:native]` — `platform = native`, the Unity test framework, `-std=gnu++17`, and a build
    filter that compiles **only** `src/pure/` so an accidental `#include <M5Unified.h>` in pure code
    fails the host build immediately rather than at the next person's desk.
- The layered directory shape ARCHITECTURE §Firmware architecture describes:
  `firmware/src/pure/` (header-only, `namespace roboface`, Arduino-free),
  `firmware/src/app/` (glue, `namespace app`), `firmware/src/main.cpp`, `firmware/test/`.
- `firmware/src/config.example.h` — `WIFI_SSID`, `WIFI_PASSWORD`, `SERVER_URL`, `DEVICE_ID`, with
  `SERVER_URL` documented as `ws://<host>:8000/ws` (see reconciliation **R1**: the server has no
  TLS). `config.h` itself is **already gitignored** and must never be committed.
- `main.cpp` compiles to a board build that boots and prints a banner — enough to prove the
  toolchain, no more.
- One host test that asserts something real (not `assert(true)`) so `pio test -e native` is a
  working command from this issue onward rather than a promise.
- Add the firmware commands to `CLAUDE.md`'s Toolchain section, which currently says to do so once
  `firmware/` lands.

**Dependencies:** None — this is the phase gate.

**Expected result:**
`pio test -e native` runs and passes, and `pio run -e cores3` compiles clean, both from `firmware/`.

**Acceptance criteria:**
- [ ] `pio test -e native` passes with at least one meaningful assertion.
- [ ] `pio run -e cores3` compiles clean, with PSRAM enabled and all three libraries resolving.
- [ ] The `native` env's build filter **excludes `src/app/`**, so pure code cannot silently acquire an
      Arduino dependency — asserted by the build itself, not by review.
- [ ] `config.example.h` exists and is committed; `config.h` is not, and `git check-ignore` confirms it.
- [ ] The Python suite is untouched: `pytest` still passes from the repo root.

### RF-013 — `ws_protocol.h` — the wire contract, mirrored and host-tested

**Description:**
The firmware half of the **WS protocol seam**. `firmware/src/pure/ws_protocol.h` is the mirror of
`server/roboface_server/protocol.py`: the same message vocabulary, the same twelve error codes, the
same `PROTO_VERSION`, the same `audio_fmt` string, the same 64 KiB cap — and the frame building and
parsing that go with them. Header-only, `namespace roboface`, no `M5`/`WiFi` include, so the whole of
it is host-tested.

ArduinoJson is used here deliberately: it compiles on the `native` platform, so parsing is testable
on a laptop rather than only on a board.

**What needs to be done:**
- **The constants, mirrored exactly** from the released `protocol.py` (reconciliation R3, R5, R6):
  `PROTO_VERSION = 1`, `AUDIO_FMT = "pcm16/16000/1"`, `MAX_TEXT_FRAME_BYTES = 65536`.
- **The message vocabulary, both directions**, as enums with string conversion: device→server
  (`hello`, `listen_start`, `audio`, `listen_stop`, `text_in`, `event`, `image_in`, `image`, `ping`)
  and server→device (`asr_partial`, `asr`, `reply`, `emotion`, `tts_audio`, `tts_end`,
  `config_updated`, `error`, `restart`, `pong`). Declare the whole set even though v0.3 exchanges
  only a few — the same reasoning that governed the server's own module.
- **`ErrorCode` with all twelve values**, including `bad_frame`. An unrecognised code parses to a
  distinct "unknown" rather than failing the frame: a device that cannot parse an error is a device
  that cannot report one.
- **Building:** `hello` (with `device_id`, `proto_ver`, `audio_fmt`, `caps`), `text_in`, `ping`.
  `caps` for the Core S3 is `touch`, `camera`, `dual_mic` — **not** `halo` (Bottom3 is v5) and **not**
  `buttons` (that is the FIRE, v6).
- **Parsing:** a server frame into a small tagged struct — `reply{text, final}`, `error{code, msg}`,
  `pong`, and "a declared type this phase does not handle" as its own outcome, distinct from
  "malformed". The server draws exactly this distinction (`UnsupportedMessage` vs `MalformedFrame`)
  and the device needs it for the same reason.
- **Reject oversize input before parsing it**, mirroring the server's rule — on a board with 320 KB
  of RAM this matters more than it does on the server, not less.
- **Seam change → ARCHITECTURE + contract test in this issue.** ARCHITECTURE §Providers and seams
  names `firmware/…/ws_protocol.h` as the firmware side of this seam; if any detail here differs
  from what the document says, the document is corrected here.

**Dependencies:** RF-012

**Expected result:**
A header-only module that builds and parses the frames v0.3 needs, pinned by host tests that run on
a laptop with no board attached.

**Acceptance criteria:**
- [ ] **Contract test** (`firmware/test/test_ws_protocol/`) pins the seam against the server's own
      contract test: both vocabularies, the twelve error codes, `PROTO_VERSION`, `AUDIO_FMT`, and the
      64 KiB cap. A value that drifts from `protocol.py` fails here.
- [ ] **Host test:** `hello` round-trips — the JSON this builds is what the server's `decode` accepts,
      field for field, including the `caps` array.
- [ ] **Host test:** a **streamed reply** parses correctly — several `final: false` frames followed by
      one `final: true` (reconciliation R2). A parser that stopped at the first frame fails this.
- [ ] **Host test:** malformed JSON, an unknown `type`, a declared-but-unhandled `type`, and an
      oversize frame each produce their **own distinct outcome** rather than one generic failure.
- [ ] No `M5`, `WiFi` or `WebSockets` include appears in this header — enforced by the `native` build
      filter from RF-012, so it is checked by compilation rather than by reading.

### RF-014 — Pure logic: the device state machine, backoff, and the line reader

**Description:**
The rest of the Arduino-free half: the device state machine ARCHITECTURE §Device states specifies,
the exponential backoff with jitter that the reconnect supervisor will drive, and the serial line
reader. All header-only in `firmware/src/pure/`, all host-tested. Independent of RF-013 — the two
can be written at the same time.

**What needs to be done:**
- **`state.h`** — `boot → wifi_connecting → idle → listening → thinking → replying → idle`, with
  `offline` and `error` reachable **from anywhere** (ARCHITECTURE §Device states). A `transition()`
  that is a total function over (state, event): every pair either produces a next state or is
  explicitly rejected, so an unhandled combination is a compile-or-test failure rather than a device
  that quietly sits in the wrong state.
  - v0.3 exercises `boot`, `wifi_connecting`, `idle`, `thinking`, `replying`, `offline`, `error`.
    `listening` is declared now and driven from v1 — it is part of the specified state set, and
    leaving it out would mean rewriting the machine rather than extending it.
- **`backoff.h`** — exponential with jitter: a base delay, a multiplier, a **ceiling**, and a reset on
  success. Jitter is not decoration — several devices rebooting after a router restart would otherwise
  reconnect in lockstep and hammer the server together. The jitter source is **injectable** so tests
  are deterministic.
- **`line_reader.h`** — accumulate bytes into a line, handle `\r\n` and `\n`, bound the buffer (a
  long paste must not be able to exhaust RAM), and drop or truncate cleanly at the limit rather than
  overflowing.
- Everything `constexpr`-friendly and free of dynamic allocation where reasonable: this runs on a
  microcontroller, and a `std::string` per serial byte is the kind of thing that works on a desk and
  fails after an hour.

**Dependencies:** RF-012

**Expected result:**
Three header-only modules carrying every decision the firmware makes, each provable without hardware.

**Acceptance criteria:**
- [ ] **Host test:** the state machine's transition table is **total** over the state × event space —
      every pair is either a defined transition or an explicit rejection, asserted exhaustively rather
      than sampled.
- [ ] **Host test:** `offline` and `error` are reachable from every state, and recovery returns to
      `idle` — the DoD's "pulling WiFi moves the device to `offline`" is this, minus the hardware.
- [ ] **Host test:** backoff grows, is capped at the ceiling, resets after a success, and **differs
      between two instances given different jitter** — the lockstep-reconnect property, tested.
- [ ] **Host test:** the line reader handles `\n` and `\r\n`, ignores empty lines, and **bounds an
      over-long line** instead of growing without limit.
- [ ] `pio test -e native` covers all of it; no test in this issue needs a board.

### RF-015 — `net` — WiFi bring-up and the reconnect supervisor

**Description:**
The first glue module: `firmware/src/app/net.{h,cpp}`, `namespace app`. Brings WiFi up from the
credentials in `config.h` and supervises it — when the link drops, it retries on RF-014's backoff
rather than a busy loop. Owns the hardware; holds no decisions of its own.

**What needs to be done:**
- Connect using `WIFI_SSID`/`WIFI_PASSWORD` from `config.h`, non-blocking, so the main loop keeps
  running and the device can show `wifi_connecting` rather than freezing.
- A supervisor stepped from the main loop: on a lost link, schedule a retry via `roboface::Backoff`
  and reconnect when it fires. **The decision of when to retry lives in the pure module**; this one
  only acts on it.
- Report link state through a small interface the state machine consumes, so `net` never sets device
  state itself — the state machine owns that.
- **Never log the WiFi password**, and never print it in a diagnostic. The server's own logging rule
  (a log has to stay safe to paste into an issue) applies to serial output too.
- Seed the jitter source from something that differs per board (the MAC or the hardware RNG), so two
  boards on one router genuinely diverge.

**Dependencies:** RF-014

**Expected result:**
The board joins WiFi, survives losing it, and comes back on its own without a reboot.

**Acceptance criteria:**
- [ ] `pio run -e cores3` compiles clean.
- [ ] The retry schedule comes from `roboface::Backoff` — no delay literals in `net.cpp`, so the
      tested logic is the logic that runs.
- [ ] The WiFi password appears in no serial output, asserted by reading every log call in the module.
- [ ] **Hardware check (DoD):** with the board running, disabling the access point moves it to
      `offline`; re-enabling it reconnects **without a reboot**, and the serial log shows the backoff
      growing between attempts.

### RF-016 — `ws` — the WebSocket client

**Description:**
`firmware/src/app/ws.{h,cpp}`: opens the WebSocket to `SERVER_URL`, sends `hello` on connect, moves
frames in both directions through RF-013's codec, answers `ping`/`pong`, and reconnects when the
socket drops. This is the module `tools/chat.py` is the Python equivalent of.

**What needs to be done:**
- Connect to `SERVER_URL` from `config.h` using `links2004/WebSockets`. **`ws://` today** — see
  reconciliation **R1**: the released server runs uvicorn with no TLS, so a `wss://`-only client
  would not connect to the thing that exists. Keep the scheme in configuration so enabling TLS later
  is a config change plus a CA bundle.
- **Send `hello` immediately on connect**, built by RF-013 — the server rejects any other first frame
  with `bad_frame`, and rejects a wrong `proto_ver` with `proto_unsupported` and a close.
- Route inbound frames through RF-013's parser and hand the result up as typed events; **binary
  frames are accepted and counted but not interpreted** — nothing gives them meaning until v1's audio.
- `ping`/`pong` both ways, and reconnect on drop using the same `Backoff` as `net` (a fresh instance,
  not a shared one: a WiFi flap and a server restart are different failures).
- Bound the inbound buffer at `MAX_TEXT_FRAME_BYTES` and drop anything larger with a logged reason,
  mirroring the server's rule (reconciliation R5).
- **ARCHITECTURE update rides here** (the seam's firmware side): record that the transport is `ws://`
  until TLS is added server-side, so the document stops promising a transport the product does not
  have. This is drift correction, not a design change.

**Dependencies:** RF-013, RF-015

**Expected result:**
The board holds an open, self-healing WebSocket to the server and exchanges typed frames over it.

**Acceptance criteria:**
- [ ] `pio run -e cores3` compiles clean.
- [ ] Frames are built and parsed **only** through RF-013's codec — no hand-rolled JSON in `ws.cpp`.
      A second implementation of the wire is exactly what the mirrored header exists to prevent.
- [ ] The inbound buffer is bounded and an oversize frame is dropped with a reason rather than
      overrunning.
- [ ] **ARCHITECTURE** records the `ws://` transport and the reason, in this commit.
- [ ] **Hardware check (DoD):** the board connects and the **server's** log shows
      `hello.negotiated` with `device_id`, `proto_ver: 1` and the Core S3 caps — verified from the
      server side, not just from the device's own claim.

### RF-017 — `main` and the serial debug channel — a turn end to end

**Description:**
The wiring, and the phase's payoff. `main.cpp` assembles the state machine, `net` and `ws`, and adds
the USB serial debug channel: a typed line becomes `text_in`, and the reply prints back as it
arrives. This is the issue the DoD's first clause is about.

**What needs to be done:**
- `setup()`/`loop()` wiring M5Unified, `net`, `ws` and the state machine, with the loop stepping each
  and never blocking — a blocking call here is what turns a responsive device into one that ignores
  its own serial port.
- **Serial in:** bytes → RF-014's `LineReader` → a `text_in` frame → sent. The device moves to
  `thinking`.
- **Serial out:** `reply` deltas printed **as they arrive**, on one line, with the terminal
  `final: true` ending the turn and returning to `idle`. This is reconciliation **R2** made visible:
  the whole point of v0.2's streaming is that the first words appear before the last are generated,
  and a device that buffered them would throw that away at the last step.
- **Errors:** an `error{code}` prints the enumerated code verbatim and moves to `error`. The code is
  the one string worth typing into a search — the same reasoning
  [features/DEVICE_UI.md](../features/DEVICE_UI.md) applies to the fault screen, which is v0.4's job.
- A small periodic status line (link, state, uptime) so a person watching the monitor can tell a
  wedged device from a quiet one.
- Update `CLAUDE.md` with the flash-and-monitor commands.

**Dependencies:** RF-016

**Expected result:**
A line typed into `pio device monitor` comes back as the model's answer, streaming, over the same
serial connection.

**Acceptance criteria:**
- [ ] `pio run -e cores3` compiles clean and `pio test -e native` still passes.
- [ ] Reply deltas are written to serial **inside** the receive path, not accumulated — a buffered
      implementation would satisfy the DoD's wording and lose the property it exists to demonstrate.
- [ ] **Hardware check (DoD clause 1):** with the server running, typing a line over serial returns
      the model's reply over serial.
- [ ] **Hardware check (DoD clause 2):** pulling WiFi moves the device to `offline`; it reconnects on
      its own and the next typed line is answered — no reboot.
- [ ] **Hardware check:** a deliberately wrong `proto_ver` (a temporary build) is rejected with
      `proto_unsupported` and the device goes to `error` rather than reconnect-looping (reconciliation
      R6).

## v0.3 scope notes

**Total effort:** ~22 points (S=1, M=3, L=5) — roughly 3 developer-weeks; the two pure modules are
the largest because they carry everything that can be tested.
**Critical path:** RF-012 → RF-013 → RF-016 → RF-017. RF-014 branches off RF-012 alongside RF-013.
**Phase DoD (roadmap §v0.3):** on the real board, typing a line over serial produces the model's
reply over serial; pulling WiFi moves the device to `offline` and it reconnects on its own;
`pio test -e native` passes and `pio run -e cores3` compiles clean.
**Contracts pinned this phase:** the **WS protocol** seam's *firmware side* —
`firmware/src/pure/ws_protocol.h`, pinned by `firmware/test/test_ws_protocol/` against the released
`server/roboface_server/protocol.py`. ARCHITECTURE is corrected in RF-016 to record that the
transport is `ws://` until TLS exists server-side.
**Explicitly out of scope, by design:** no audio (v1), no face or renderer (v0.4 — v0.3's screen shows
nothing but a boot banner), no touch/IMU/proximity reactions (v2), no camera (v3). The device sends
`text_in` and nothing else.
**Hardware note:** three acceptance criteria (RF-015 and RF-017) can only be checked on a real Core
S3. The rest — both pure modules and both compiles — are verifiable on a laptop, which is why the
phase is split the way it is.
**Model note:** chat runs on **Gemini 2.5 Flash only** (`thinkingBudget: 0`) behind the `LLMProvider`
seam; **no paid APIs** — the firmware's host tests touch no network at all, and the hardware checks
use the same server every other phase does.
