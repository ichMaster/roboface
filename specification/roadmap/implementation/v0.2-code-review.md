## Findings

### 1. 🔴 HIGH — `repr(Settings)` prints the API key in full

**Where:** [config.py](../../../server/roboface_server/config.py) — `Settings` is a plain
`@dataclass(frozen=True, slots=True)`, so its generated `__repr__` includes every field.

**Reproduced:**

```
repr(settings) -> Settings(ws_host='0.0.0.0', ws_port=8000, log_level='info',
                           gemini_api_key='AIzaSyTOTALLY-SECRET-KEY-12345', …)
```

**Failure scenario.** Any of the ordinary ways an object reaches text: an unhandled traceback
from a framework that renders locals; `log("startup", settings=settings)` — which the logging
module would happily serialise, since `JsonFormatter` passes `default=str`; a `print` while
debugging; a crash reporter. The key is 39 characters of live credential, and the project's
own rules are explicit — MISSION and ARCHITECTURE §Configuration keep secrets server-side, and
the v0.1 review's standard for a log line is that it stays *safe to paste into an issue*.

Nothing in the tree does any of these **today**. That is what keeps it out of the "already
leaking" category — and it is not a reason to leave a loaded object lying in the one module
whose whole job is handling secrets. The fix is four lines.

**Proposed fix.** A custom `__repr__` on `Settings` that renders the key as `***` when set and
`unset` when empty — never a prefix, never a length. Both of those are still information about
a credential, and neither helps debugging more than the boolean does.

### 2. 🟠 MEDIUM — An untranslated responder exception kills the connection, with no `error` frame

**Where:** [router.py `_stream_reply`](../../../server/roboface_server/router.py) — the loop
catches `TurnAborted` and nothing else.

**Reproduced** — a responder that raises `KeyError` mid-stream:

```
CONNECTION DIED: KeyError: 'a bug nobody translated'
```

The device receives **nothing** — not the deltas that had already been produced, not an
`error{code}`, not a clean close. It sees the socket drop.

**Failure scenario.** Any bug inside a responder or a provider adapter that isn't a
`ProviderError`: a `KeyError` in history handling, a `pydantic` validation error from an SDK
shape that changed, an `AttributeError` after a refactor. v0.1's `EchoResponder` could not
raise, so this is a **robustness regression introduced by v0.2** — and it is worse than a
failed turn, because the device must notice the dead socket, back off and reconnect rather
than render the error face and carry on. ARCHITECTURE §Budgets and abort semantics is explicit
that a failed turn "returns the device to `idle`" and "the session stays connected".

`ErrorCode.internal` exists for exactly this: the server broke. Nothing currently sends it.

**Proposed fix.** Catch `Exception` (not `BaseException` — `CancelledError` must keep
propagating), send `error{internal}`, log it at `error`, and keep the connection. This is the
same lesson as v0.1's finding 3, one layer up.

### 3. 🟠 MEDIUM — Provider status hints misattribute fault to the wrong party

**Where:** [providers/gemini.py `_STATUS_HINTS`](../../../server/roboface_server/providers/gemini.py)
— `401/403 → unauthorized`, `503 → server_unreachable`.

**Failure scenario.** Gemini returns 503 (its own outage). The device is handed
`server_unreachable`, and per [DEVICE_UI.md](../features/DEVICE_UI.md) §Screens a fault renders
the enumerated code verbatim with its line — the document's own worked example is literally
**"No server · `server_unreachable`"**. So the screen tells the person the device cannot reach
its server, **while it is connected to that server and being told so over that connection.**
The one fault message a user could act on is the one that is wrong.

`401/403` has the same shape: our *server's* Gemini key being bad is not the *device* being
unauthorized. The device did nothing, and can do nothing about it.

This is the identical "whose fault is it" analysis that produced `bad_frame` in RF-009 —
applied one layer out, to the provider hints, where it was got wrong. The irony is the point:
the distinction was fresh and still missed on the outbound side.

**Proposed fix.** `429 → rate_limited` (correct — it *is* rate limiting) and `504 → llm_timeout`
(correct — the LLM leg timed out) both stay. `401/403/503` become **unhinted**, so the
orchestrator maps them to `llm_failed` in the one place that exists for it. The real cause is
not lost: it is logged server-side, where the person who can fix a bad key will actually look.

### 4. 🟠 MEDIUM — The turn invariant is not total

**Where:** [orchestrator.py `_run_turn`](../../../server/roboface_server/orchestrator.py).

A turn is supposed to have exactly two endings: it completes (append the model message) or it
aborts (roll the user message back). **There is a third**: the consumer stops iterating, and
neither happens.

**Reproduced** — a consumer that abandons the stream after two deltas:

```
consumed: ['a', 'b'] | provider stream cleaned up: 0
history after abandoned turn: [('user', 'hi')]
```

The user message is stranded with no reply, and the provider's generator — which in the real
adapter holds an open HTTP response — is left to garbage collection.

**Failure scenario, and its honest status.** Through the router *today* this is unreachable:
the only way to abandon the loop is an exception from `transport.send`, which tears the
connection down and `forget()` clears the session. **It becomes reachable in v3.4**, where
ARCHITECTURE §Budgets and abort semantics has barge-in *"cancel a turn"* while the session
continues — at which point the next turn shows the model a question it never answered, which
is precisely the inconsistency the rollback in RF-009 exists to prevent.

The reason to fix it now rather than schedule it: an invariant with three outcomes is not an
invariant, and this one is asserted in four tests that all pass while a fifth outcome exists.
The fix is a `finally`, not a design.

**Proposed fix.** Wrap the turn body so that on `GeneratorExit`/cancellation the user message
is rolled back and the provider stream is closed — making "completed or rolled back" total.

### 5. 🟠 MEDIUM — Session history is unbounded, and resent whole every turn — DEFER → v4.2

`Orchestrator._history[session_id]` grows by two messages per turn with no cap, and
`_run_turn` passes `tuple(history)` to the provider every time. A long-lived connection
therefore costs more per turn than the last, indefinitely, and eventually meets the model's
context limit as an `llm_failed` nobody can explain.

Bounded in practice by connection lifetime (`forget()` clears at teardown), which is why this
is MEDIUM rather than HIGH. **Deferred deliberately:** ARCHITECTURE §Data model already
specifies the answer — `SessionMessage` with *"the rolling 40-message window"* — and assigns it
to **v4.2 (Memory)**. Implementing a window here would pre-empt that design with a worse one
written without its requirements, and the roadmap rule is that a version does not pull a later
version's concern forward.

### 6. 🟡 LOW — Two exception types for one condition — DEFER → cleanup

`config.Settings.require_gemini_api_key()` raises `ConfigError`; `GeminiProvider("")` raises
`ProviderError(UNAUTHORIZED)`. `build_responder` calls the former first, so the latter is only
reachable by constructing the provider directly. Harmless today, but a caller catching one
type will one day be surprised by the other. Worth collapsing when the deployment story lands.

### 7. 🟡 LOW — `main()` surfaces a `ConfigError` as a traceback — DEFER → deployment story

The message names the variable and the file, which is the important half; the presentation is a
Python traceback rather than a line on stderr and a non-zero exit. Same home as v0.1's finding
7 (`create_app` and the `--factory` invocation) — these want doing together, once, when there
is a Dockerfile to be right about.

### 8. 🟡 LOW — A bare `TimeoutError` from a provider is misreported — DEFER → cleanup

`_run_turn` catches `TimeoutError` to mean "the first-token budget expired". Since Python 3.11
`asyncio.TimeoutError` *is* `TimeoutError`, so a provider that lets an HTTP read timeout escape
would be reported as a budget breach at whatever moment it happened, including mid-stream. The
Gemini adapter translates everything, so this needs a *different*, badly-behaved provider to
bite. Fixing it properly means distinguishing "our `wait_for` fired" from "something else timed
out" — a small refactor, but not one to make while the only provider cannot trigger it.

## What's solid

- **A finding was withdrawn under its own probe.** The timeout path looked like it must leak
  the provider's HTTP stream — `wait_for` cancels `anext` and nobody calls `aclose()`. The
  probe showed cleanup runs *immediately*: cancellation throws into the generator at its
  suspension point and its `finally` executes. The design is right; the suspicion was not.
- **The streaming property is tested in a way that can fail.** `test_deltas_arrive_while_the_
  model_is_still_generating` was verified against a deliberately buffering router that still
  emitted the same five frames — it fails there and passes nowhere else. That is the difference
  between testing streaming and counting frames.
- **The seam paid for itself twice.** RF-010 (Gemini) and RF-008 (orchestrator) were built
  against each other's absence, and the entire suite still runs with `google-genai` uninstalled
  and no API key.
- **`bad_frame` landed properly.** All three codec exceptions and all five router rejections
  moved together, ARCHITECTURE and both contract tests changed in the same commit, and the
  contract test caught the enum change by itself before any human looked.
- **The paid call is guarded twice and the guards are asserted**, including that an explicit
  `pytest tests/live` still skips without the opt-in.
- **The live DoD check earned its place** — it surfaced the SDK's per-turn stderr warning,
  which no mocked test could ever have shown.
