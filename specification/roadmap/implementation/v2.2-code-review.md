## 1. 🔴 HIGH — the mouth freezes mid-reply again

**Where:** `firmware/src/app/procedural_renderer.cpp:106` (`show(const EmotionFrame&)`), against
`server/roboface_server/router.py` (`_stream_reply`, the end-of-turn frame).

**Failure scenario, and it is every reply rather than an edge case:**

1. The turn ends on the server. It sends `emotion{neutral, speaking: false}` and `reply{final: true}`.
2. The device is **seconds behind** — measured at 244 KB of buffered audio, about eight seconds of
   voice still to play. That gap is the whole reason v2.1.2 exists.
3. `show(frame)` runs `speaking_allowed_ = frame.speaking`, so the permission is withdrawn while
   `playing_` is still true.
4. `mouthRuns(speaking_allowed_ || speaking_mouth_, playing_)` is now `false`. **The mouth shuts and
   stays shut for the rest of the reply.**
5. `idle_.setIntensity(1.0f)` and `setBlinking(true)` run in the same call, so the breathing drift
   comes back over a face that is still talking.

Both halves of what was reported as two separate faults before v2.1.2 — "рот перестає рухатись" and
"коли він говорить то далі відбувається дріфт" — come back together, and this time the instruction
arrives from the server rather than from the device's own state machine.

**Why the regression test did not catch it.** `test_facehold.cpp` asserts
`mouthRuns(false, true) == false`, which is correct and is the rule. What it does not test is *what
sets the first argument*: the renderer withdraws the permission the moment the server says the turn
is over, so the rule is being asked the wrong question. A pure function can only be as right as its
inputs, and the input is decided one layer up — which is exactly where nothing was testing.

**Proposed fix.** Honour what ARCHITECTURE already says: *"`speaking` is a permission, not a
duration … what stops the mouth is the device's own playback state."* A frame that withdraws the
permission while the device is still playing is an instruction about a moment that has not arrived,
so **hold it and apply it when playback ends**. The router says as much in its own comment — "an
instruction to relax, not a description of now" — and the device is the half that was not
implementing it.

Concretely: a frame with `speaking == false` arriving while `playing_` is queued rather than
applied; `setPlaying(false)` applies it. A frame with `speaking == true` always applies at once, and
so does any frame when nothing is playing. A device-local `show(DeviceState)` clears the queue,
because a dropped link outranks a queued instruction from the server that dropped.

**Regression test.** At the renderer's level rather than the pure function's, because that is the
layer that was wrong: feed the exact sequence the server produces — a speaking frame, then the relax
frame while playing, then playback ending — and assert the mouth ran throughout and shut only at the
end. The pure `mouthRuns` test stays; it was never wrong.

## 2. 🟠 MEDIUM — a ttl that outlives the connection it came from

**Where:** `firmware/src/app/procedural_renderer.cpp` — `show(roboface::DeviceState)` does not
touch `hold_`.

**Failure scenario:**

1. Mid-reply, the socket drops. The last frame in force was `replying`, whose ttl is 60 s.
2. `main.cpp` sets `server_face = false` and the device shows its own `offline` face — sad, dimmed
   to ~60 %, which is what DEVICE_UI §Screens specifies for a device that cannot reach its server.
3. Up to 60 s later `FaceHold` expires. The renderer crossfades to `neutral` and restarts the idle
   loop **over a device that is still offline**, and the chrome's fault indicator is left arguing
   with a face that looks fine.

The window is as long as the ttl of whatever frame happened to be standing, so the symptom is
intermittent by construction — the worst kind to diagnose from a photograph.

**Proposed fix.** `show(DeviceState)` releases the hold. The device-local states are not things that
expire; that is the distinction `FaceHold::release()` was written for and it simply is not called.

**Regression test.** `pio test -e native`: hold a frame, take the device's own face back, advance
past the ttl, assert nothing expired.

## 3. 🟠 MEDIUM — a late model report is silently dropped

**Where:** `server/roboface_server/orchestrator.py` — the `replying` frame is built from
`stream.report` at the moment the first delta arrives, and never revisited.

**Failure scenario:**

1. The model emits its `reply` text before its `emotion` field. The response schema declares the
   report first and pins `property_ordering`, so Gemini does not do this — but the **seam** does not
   promise it. `LLMProvider.stream`'s own docstring says the two "arrive interleaved on one
   connection", the mock can produce any order, and a future provider revision is exactly the kind
   of thing that changes a serialisation detail.
2. At the first delta `stream.report` is still `None`, so the frame goes out as `neutral`.
3. The report arrives mid-stream. `_ReplyStream` records it faithfully. **Nothing reads it again.**
4. The device wears `neutral` for the whole of a reply the model labelled `joy` — and the failure is
   invisible: a plausible face, a complete reply, no error anywhere.

**Proposed fix.** In the delta loop, notice when `stream.report` has changed since the frame was
emitted and yield an updated `EmotionEvent`. Small, and it makes the ordering guarantee an
optimisation rather than a requirement — which is what a seam that admits interleaving should mean.

**Regression test.** A mock provider that reports **after** its deltas; assert the turn still ends
with the model's emotion on the wire.

## 4. 🟡 LOW — `ttl_ms` is unbounded above

`protocol._optional_ttl` rejects zero and negatives; the firmware does the same. Neither caps the
upper end, so `ttl_ms: 4294967295` pins a face for about 49 days. Harmless from our own server and
not worth a clamp in this phase, but it is the same class of input hygiene as the frame-size cap.

**Home:** v5.1 (resilience), alongside the other bounds.

---

## 5. 🟡 LOW — `ObjectStream` buffers unbounded scalar strings

A string field that is *not* in `stream_keys` accumulates in `_buffer` until it closes. In practice
the response is bounded by the model's output limit, so this is bounded by something — just not by
us. Worth a cap when the resilience pass adds the others.

**Home:** v5.1.

---

## 6. 🟡 LOW — `speaking_mouth_` reads as dead code and is not

Since v2.2 the renderer's `show(DeviceState)` is only called for device-owned states, so
`speaking_mouth_` — set from `state == kReplying` — appears unreachable. It is not: it is the path a
server that sends **no** `emotion{}` frames still takes, which is not hypothetical, as this phase
discovered when the board turned out to be talking to a different machine on the LAN for the whole
of RF-063.

The risk is a future cleanup deleting it as dead. It wants a comment saying what it is, not a change.

**Home:** documentation, in the next pass over that file.

## What's solid

- **The coercion discipline.** `emotion{}` is the one frame both decoders refuse to reject, and the
  reasoning is written down in three places rather than assumed. `from_model` is total over
  arbitrary input and the tests hammer it with `object()`, NaN, and booleans-as-numbers.
- **`jsonstream.py`.** Fed the same document at every chunk size from one character upward, with
  boundaries inside escapes and between the halves of a surrogate pair, and reassembling
  byte-identically each time. The per-character-delta mistake was caught while the tests were being
  written rather than on the wire.
- **The abandonment invariant.** RF-062 found that the new first yield sat outside `_run_turn`'s
  `try`, which had quietly restored the third ending v0.2 closed. The tests that found it were
  written for a different reason two phases ago, which is the best evidence they were worth writing.
- **Cross-tier agreement is now checked.** `test_firmware_mirror.py` compares the two `Emotion`
  enums and the frame defaults across C++ and Python. That drift would have been silent: an unknown
  value coerces to `neutral`, and the only symptom is a character that seems oddly flat.
