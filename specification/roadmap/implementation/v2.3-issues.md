# v2.3 — GitHub Issues

Issues for phase **v2.3 — Lip-sync** (version **v2 — Living face**), derived from the per-phase
Tasks in [ROADMAP.md](../../ROADMAP.md) (§v2.3) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§The face, §EmotionFrame, §Audio pipeline). This file is
scoped to a single phase; IDs continue from the previous phase (RF-063 → **RF-064…RF-066**).

**This phase is smaller than the roadmap implies, and the reason is on the record.** During v2.1 the
user asked for lip-sync ahead of schedule — *"додай зараз спрощену версію Ліпсинк"* — and `v2.1.2`
shipped it: discrete mouth shapes with hysteresis, an opening that is geometrically separate from the
expression's curve, and the playback level wired through `setAudioLevel`. v2.2 then fixed the gating
so `speaking` is a permission rather than a duration.

So three of the four Tasks are done, and pretending otherwise would produce issues that reimplement
working code. What remains is the part that was **approximated**:

| Task (roadmap §v2.3) | State after v2.1.2 / v2.2 | This phase |
|---|---|---|
| Pure-logic envelope: **windowed RMS** + band mapping | driven by `peakLevel` — a peak over a 32 ms window | **RF-064** |
| Feed it from the playback ring without stalling I2S | done — `AudioIo::tick` computes it where the samples are already in hand | — |
| Layer the viseme over the expression mouth; restore it when `speaking` is false | done — `open_height` is a separate field from `mouth_curve`, and v2.2's review fixed *when* it stops | — |
| Tune smoothing so the mouth reads as speech rather than noise | thresholds spread by hand against one measurement | **RF-065** |
| DoD: *"animates in time with the audio"* at ~15–20 FPS | the mouth is redrawn at 8 FPS while speaking | **RF-066** |

**Why the envelope is the gate.** The peak over a 32 ms window of continuous speech sits near
full-scale almost the whole time — measured on the board, `lvl=0..93%` per ten-second window with the
mouth changing shape four times in the first version of the ladder. The fix applied then was to
spread the thresholds across the observed range, which worked and is a workaround: it compensates for
a signal whose *shape* is wrong. RMS over a window is the measure the roadmap specifies and the one
that actually varies with speech, and every threshold in `lipsync.h` is calibrated against the signal
it is fed — so the envelope has to change before the tuning means anything.

## v2.3 — Lip-sync

### RF-064 — The RMS envelope, against real PCM

**Description:**
Replace the peak detector that drives the mouth with the windowed RMS envelope the roadmap
specifies, and test it against actual samples rather than against synthetic level values. Touches
`firmware/src/pure/level.h` (or a new `envelope.h`), `firmware/src/app/audio_io.cpp` and
`firmware/test/`.

**What needs to be done:**
- **A windowed RMS envelope in pure logic.** Root-mean-square over the playback chunk, which is
  512 samples / 32 ms at 16 kHz — the unit the audio path already hands over, so no buffering is
  added and I2S is not touched.
- **Keep `peakLevel` for the input meter, and say why.** `level.h`'s own comment is right about the
  meter: *"the person is using this to confirm the device is hearing them now, so the number that
  matters is the loudest sample in the frame rather than the average energy of it."* That argument
  is about a meter a person is watching for a response; it does not transfer to a mouth, which is
  modelling how open a jaw is. **Two consumers, two measures** — and the comment must stop reading
  as though one rule covered both.
- **Asymmetric smoothing, and the asymmetry stated.** Speech has hard onsets and soft decays: rising
  fast makes a consonant land, falling slowly stops the mouth flickering shut between syllables.
  The existing `decayToward` already does exactly this and is reused rather than reinvented — what
  changes is what it is fed.
- **PCM fixtures, in the test rather than in a file.** Generated in C++ from parameters, because a
  binary blob in the repository cannot be read by the next person and cannot be adjusted: silence,
  a steady tone, a speech-like burst train with gaps, and a clipped signal. Roadmap §v2.3's Tests
  names exactly these three cases plus smoothing.
- **The property that matters, asserted directly:** over a speech-like signal the RMS envelope must
  *vary* — its interquartile range must be a substantial fraction of its maximum. A measure that
  sits pinned near the top is the defect this issue exists to remove, and "it compiles and returns
  a number" would not catch it.

**Dependencies:** None

**Expected result:**
The mouth is driven by a signal that moves with speech instead of one that saturates on it.

**Acceptance criteria:**
- [ ] **Unit test** (`pio test -e native`): RMS over silence is 0; over a full-scale tone it is the
      expected constant (≈0.707 for a sine); over a clipped signal it does not exceed 1.0
- [ ] **Unit test:** over a speech-like fixture the envelope's spread is a large fraction of its
      maximum — the property a peak detector fails
- [ ] **Unit test:** smoothing rises faster than it falls, with both rates pinned
- [ ] `peakLevel` is unchanged and still used by the input meter, with the two uses documented apart
- [ ] `pio run -e cores3` compiles; no `M5` include reaches `src/pure/`

### RF-065 — The viseme bands, calibrated to the envelope

**Description:**
`lipsync.h`'s thresholds were spread by hand across one measurement of the old peak signal. Against
an RMS envelope they are wrong by construction. Recalibrate them — from the fixtures, not by feel —
and pin the result. Touches `firmware/src/pure/lipsync.h` and its tests.

**What needs to be done:**
- **Re-derive `opens_at` / `closes_at` from the RMS fixtures**, so each band covers a comparable
  share of a speech-like signal. A ladder where one band takes 90% of the time is four shapes doing
  the work of one, which is what the peak signal produced.
- **Keep the hysteresis and state its size in terms of the new signal.** The gap between opening and
  closing is what stops a level sitting on a threshold from flickering between two shapes on adjacent
  frames — a flutter that looks wrong *and* costs more redraws than the smooth mouth it replaced.
- **Keep the five shapes and the alternating widths.** The roadmap says four bands
  (closed/small/mid/wide); the implementation has five, and each has a spread and a pursed variant
  that alternate per syllable. That was measured to be better — it is what took the mouth from four
  shape changes per ten seconds to eighty — so **`ARCHITECTURE.md` records the table as the
  authority and the count as data**, rather than the roadmap's number being quietly wrong.
- **A test that the bands are actually used.** Run a speech-like fixture through the envelope and
  the ladder together and assert every band is entered. A band no signal ever reaches is dead code
  that looks like tuning.

**Dependencies:** RF-064

**Expected result:**
Each mouth shape earns its place: a real speech signal visits all of them, and none dominates.

**Acceptance criteria:**
- [ ] **Unit test:** a speech-like fixture through envelope + ladder enters **every** band
- [ ] **Unit test:** no single band holds more than a stated share of the frames
- [ ] **Unit test:** the flutter case — a level held between two thresholds produces one shape, not
      an alternation
- [ ] `ARCHITECTURE.md` §The face records that the viseme ladder is a table and what its rows mean
- [ ] The alternating spread/pursed widths survive, with their test

### RF-066 — The mouth's frame rate, and what it costs

**Description:**
The DoD says the mouth animates *in time with the audio*. It is currently redrawn every 120 ms —
about 8 FPS — against a roadmap that asks for 15–20. Raise it, and **prove it does not cost the
audio path**, which is the trade this project has got wrong three times. Touches
`firmware/src/main.cpp` and the on-board measurement.

**What needs to be done:**
- **Raise the speaking-state frame interval** toward the 50–65 ms the roadmap's rate implies.
- **Measure, do not assume.** The status line already reports `fps`, `mic` and `mouth`; the claim to
  defend is that raising the face's rate while speaking leaves capture unaffected. It should:
  half-duplex suspends the microphone during playback, so these frames compete with nothing — but
  that is a prediction, and this project has twice found the opposite. The numbers before and after
  go in the execution report.
- **Leave the listening and idle intervals alone.** Those were set from measurements where the
  microphone *was* running, and the reason is recorded next to them: at 18 FPS capture collapsed to
  35% of a window. Nothing here changes that finding; this issue is about the one state where the
  microphone is off.
- **A guard, not a hope.** If the measurement shows capture or playback suffering, the interval goes
  back and the issue records the number rather than the intention. The rule stands: *the face may
  drop frames, the microphone may not.*

**Dependencies:** RF-065

**Expected result:**
The mouth is redrawn fast enough to read as speech, with the audio path measurably unaffected.

**Acceptance criteria:**
- [ ] The speaking-state interval yields ≥15 FPS on the board, read from the status line
- [ ] `mic` during playback is unchanged from the v2.2 baseline (the microphone is suspended then,
      so the expected answer is "unchanged" — and it is asserted rather than assumed)
- [ ] `drop` and `ref` stay at zero through a long reply
- [ ] The before/after numbers are in `v2.3-execution-report.md`
- [ ] Ties to the phase DoD: the mouth animates in time with the audio

## v2.3 scope notes

**Total effort:** roughly 9 points (M+M+M) — smaller than v2.2 because `v2.1.2` already delivered
three of this phase's four Tasks, out of order, at the user's request.

**Critical path:** RF-064 → RF-065 → RF-066, and the chain is genuinely serial: thresholds are
meaningless until the signal is right, and a frame rate is meaningless until what is drawn changes
at a rate worth showing.

**Phase DoD (roadmap §v2.3):** while the device speaks, the mouth animates in time with the audio;
when it stops, the expression's own mouth returns; the server sends nothing per frame for any of it.

**Contracts pinned this phase:** none of the five seams moves. `EmotionFrame` already carries
`speaking` and deliberately carries no level — ARCHITECTURE §EmotionFrame states that lip-sync is
local, from the playback buffer, and this phase is the strongest form of that claim: the server
sends nothing at all for the mouth. `ARCHITECTURE.md` §The face gains a description of the viseme
ladder, which is documentation of what the table means rather than a contract change.

**Model note:** no provider is involved. This phase touches no server code at all — it is the one
phase whose whole content is on the device, which is exactly what "lip-sync is local, for latency"
was always going to mean.
