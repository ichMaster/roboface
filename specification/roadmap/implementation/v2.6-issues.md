# v2.6 — GitHub Issues

Issues for phase **v2.6 — Spirit skins and the carousel** (version **v2 — Living face**), derived
from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§v2.6) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§EmotionFrame, §The face, §IFaceRenderer). IDs continue
from the previous phase (RF-077 → **RF-078…RF-083**).

Five faces, one contract. This is the phase where *"a skin is an asset swap"* stops being a rule in
`CLAUDE.md` and becomes a property the code cannot violate — and the way to make it one is to move
the procedural face itself onto the same footing as the four spirits. If stackchan is special, every
future skin will need a little renderer logic; if stackchan is a manifest, none of them can.

## Reconciliation notes (Step 0.5)

Read against the real code and against the executable reference:

- **`specification/face-prototype.html` is the design, and CLAUDE.md forbids inventing a second
  one.** Its structure is already exactly a manifest: `sEyes(emotion, lx, rx, y, ink, hi, gx)` and
  `sMouth(emotion, cx, cy, ink)` are the shared expression grammar, and each of the five skins
  supplies a silhouette, anchor coordinates, an ink and highlight colour, and an **element** — the
  ghost's blush and tear, the flame's palette, the jelly's glow, the cloud's weather. The manifest
  schema is that argument list, made data.
- **`ProceduralRenderer` currently holds stackchan's geometry as constants** and its gaze authority
  as three members (reflex, voice, server, since v2.5). The renderer's inputs are already right; what
  is hard-coded is *which face* they draw.
- **`pure/face.h` already carries the emotion grammar** — `FaceGeometry`, the recipe table, and the
  per-emotion eye and mouth shapes. Manifests parameterise it rather than replacing it.
- **v2.5's lesson carries forward:** the phase's hardest defect (`chooseSource`) was a decision
  remade every frame with no memory, and its sibling (`frame_for(gaze=…)`) was a parameter with no
  caller. Both are shapes this phase can easily repeat — a skin switch is a decision, and a manifest
  field nothing reads is a manifest field that will drift.
- **The carousel's gesture already exists.** `TouchGesture::kHeldSilent` has been produced by
  `pure/touch.h` since v2.4 and consumed by nothing. This phase is where it acquires a consumer, or
  the finding is that it should not exist.

## v2.6 — Spirit skins and the carousel

### RF-078 — The skin manifest: a schema that is total over the emotions

**Description:**
The data a skin is. New `firmware/src/pure/skin.h` — header-only, Arduino-free, and host-tested
against the property that matters most: **every skin answers for every emotion**.

**What needs to be done:**
- The schema, derived from `face-prototype.html`'s own argument lists rather than invented: eye
  anchors (`left_x`, `right_x`, `y`), mouth anchor (`cx`, `cy`), ink and highlight colours, the
  background, gaze travel in pixels, and the **element** — the one thing each spirit does that the
  others do not.
- **The element is a small closed enum, not a script.** `kNone`, `kBlushAndTear` (ghost),
  `kPaletteFollowsEmotion` (flame), `kGlowFollowsEmotion` (jelly), `kWeatherFollowsEmotion` (cloud).
  A skin that needed a sixth would be telling us the design is wrong, and an enum is where that
  shows up immediately rather than three phases later.
- **Per-emotion overrides as a total table.** A skin may tint an emotion differently; it may not
  leave one undefined. The test is the schema's real content: iterate `Emotion` and assert every
  entry resolves.
- `validate()` returning a reason rather than a bool — a pack that fails must say which field, since
  RF-083's fallback logs it and a boolean would make every failure look the same.

**Dependencies:** None

**Expected result:**
`roboface::Skin` describes a face completely, and a skin missing an emotion cannot compile or cannot
validate.

**Acceptance criteria:**
- [ ] **Unit test:** every `Emotion` resolves to a recipe for every built-in skin — iterated over the
      enum, not spelled per skin, so a new emotion breaks every skin at once rather than silently.
- [ ] **Unit test:** `validate()` names the offending field for each way a manifest can be wrong.
- [ ] **Unit test:** anchors outside the face safe area are rejected — a skin cannot draw over chrome.
- [ ] Compiles under `pio test -e native`; no `M5` include reachable.

### RF-079 — The procedural face becomes a manifest like any other

**Description:**
Express stackchan in the schema and make the renderer read manifests. Touches
`firmware/src/app/procedural_renderer.{h,cpp}` and `firmware/src/pure/face.h`.

**What needs to be done:**
- A `stackchan` manifest reproducing today's face exactly, and the renderer's hard-coded geometry
  deleted rather than left beside it.
- `IFaceRenderer` gains skin selection; the recipe path takes ink and anchors from the manifest.
- **The proof this issue exists for:** anything the procedural face still needs that the schema
  cannot express is a hole in RF-078, and it is found here or it is found by the fourth spirit.
- The gaze authority added in v2.5 (reflex → voice → server → drift) is untouched: it is about
  *where* the face looks, not *what* face it is.

**Dependencies:** RF-078

**Expected result:**
The device looks identical to v2.5 and no longer contains a face-specific constant in the renderer.

**Acceptance criteria:**
- [ ] **Unit test:** the stackchan manifest's geometry equals the constants it replaced, value by
      value — the regression that would silently change the face nobody was looking at.
- [ ] No skin-specific literal remains in `procedural_renderer.cpp` — asserted by review, stated here.
- [ ] **Contract test:** `IFaceRenderer` + the manifest, per the pinned seam; `ARCHITECTURE.md`
      updated in the same commit.
- [ ] On hardware: the face is unchanged from v2.5.

### RF-080 — The four spirits

**Description:**
Ghost, flame, jellyfish and cloud, authored against the shared grammar. `assets/` and their
manifests.

**What needs to be done:**
- Four manifests, each a silhouette, anchors, palette and one element, ported from
  `face-prototype.html` — its coordinates are the coordinates, not an inspiration.
- The elements: the ghost's blush and tear; the flame's palette following the emotion; the jelly's
  glow following it; the cloud's weather. Each is the enum value from RF-078 plus its parameters.
- **No renderer change may be needed by any of them.** If one is, the finding belongs in the review
  and the schema is wrong — that is the phase DoD stated as a working rule.

**Dependencies:** RF-079

**Expected result:**
Five skins render the same `EmotionFrame`, and four of them arrived without touching the renderer.

**Acceptance criteria:**
- [ ] **Unit test:** all five manifests validate and are total over `Emotion`.
- [ ] **Unit test:** each element's parameters resolve for every emotion — the flame's palette and
      the cloud's weather are per-emotion tables and must be total for the same reason the recipes are.
- [ ] The diff for this issue touches no renderer file. Asserted by the diff itself.
- [ ] On hardware: each of the four renders and expresses at least joy, sad and error distinctly.

### RF-081 — `config_updated{face_set}`, and the active skin in `hello`

**Description:**
Switching from the server, and the device saying which skin it is wearing. Touches
`server/roboface_server/protocol.py`, the router, `firmware/src/pure/ws_protocol.h`, and
`ARCHITECTURE.md`.

**What needs to be done:**
- `config_updated{face_set}` as a server→device frame, with the skin name validated against the
  manifest set — an unknown name is refused and logged, never silently ignored.

  tell what it is looking at.
- **A seam change**: `ARCHITECTURE.md` and its contract test in the same commit, on both sides of

- Persist the choice across a reboot, or state explicitly that it does not and why.

**Dependencies:** RF-079

**Expected result:**
The server can change the face, and the device says which one it has.

**Acceptance criteria:**
- [ ] **Contract test:** the `config_updated` frame round-trips; an unknown `face_set` is refused
      with the enumerated error rather than accepted.
- [ ] **Contract test:** `hello` carries the active skin, and the firmware mirror agrees.
- [ ] **Integration test:** a fake device is switched and reports the new skin on reconnect.
- [ ] `ARCHITECTURE.md` updated in the same commit.

### RF-082 — The carousel, and who owns the bottom band

**Description:**
The on-device way to change face, and the arbitration that keeps three tenants out of one band.
Touches `firmware/src/pure/`, `app/chrome_view.*` and `main.cpp`, against
[DEVICE_UI.md](../../features/DEVICE_UI.md) §Input and §Screens.

**What needs to be done:**
- `TouchGesture::kHeldSilent` — produced since v2.4, consumed by nothing — finally drives something:
  the dot strip, slide to choose, release to confirm, whisper toast on change.
- **Bottom-band arbitration: carousel > toast > level meter, one tenant at a time.** `pure/chrome.h`
  already has `BandTenant` and decides between a fault and the meter; this extends that decision
  rather than adding a second one beside it.
- The gesture's own rules stay in `pure/touch.h`; the drawing stays in `chrome_view`; the arbitration
  stays pure and host-tested. Three files, three concerns, as the rest of the chrome already is.

**Dependencies:** RF-080, RF-081

**Expected result:**
Holding the face for 1.2 s without speaking opens the carousel; sliding chooses; releasing confirms.

**Acceptance criteria:**
- [ ] **Unit test:** the band's tenant is decided by documented priority, including every pair that
      can be live at once.
- [ ] **Unit test:** a hold that becomes speech never opens the carousel — the PTT rule from
      DEVICE_UI, and the regression that would make the device stop listening when someone paused.
- [ ] **Unit test:** releasing outside the strip cancels rather than choosing the nearest.
- [ ] On hardware: the carousel opens, slides, confirms, and the toast fades.

### RF-083 — A missing or broken pack degrades to the procedural face

**Description:**
The DoD's robustness clause, and the one that decides whether this phase can ship on a device with
an SD card in it. Touches the skin loading path and `main.cpp`.

**What needs to be done:**
- Load a pack at `begin()`; on any failure — absent, unreadable, invalid, incomplete — fall back to
  the procedural face **and say so on serial**, naming the field that failed.
- **A face is never absent.** A device that cannot draw a face has no way to tell anyone anything,
  so the fallback is not an error path, it is the definition of the feature.
- v2.4's lesson applies literally: `begin()` must not report success for a pack it did not load.
  Asking whether a file exists and asking whether it validated are different questions.

**Dependencies:** RF-080

**Expected result:**
No pack, a truncated pack and a pack missing an emotion all produce the procedural face and a
serial line naming why.

**Acceptance criteria:**
- [ ] **Unit test:** each failure mode falls back and reports a distinct reason.
- [ ] **Unit test:** a valid pack is *not* silently replaced by the fallback — the mirror-image bug,
      and the one nobody would notice.
- [ ] On hardware: a deliberately corrupted pack boots to the procedural face with a stated reason.

## v2.6 scope notes

**Total effort:** roughly 26 points across 6 issues (L, L, M, M, L, M).
**Critical path:** RF-078 → RF-079 → RF-080 → RF-082.
**Phase DoD (roadmap §v2.6):** all five faces render the same `EmotionFrame` correctly and are
switchable both ways; adding a skin requires no renderer code change; a corrupt or missing pack
degrades to the procedural face instead of failing; **v2 is the complete living face**.
**Contracts pinned this phase:** `IFaceRenderer` + the skin manifest, and the `config_updated`
frame — both with their `ARCHITECTURE.md` updates and contract tests in the issues that change them.
**Model note:** chat runs on **Gemini 2.5 Flash only** (`thinkingBudget: 0`); no paid APIs in tests.

**The structural risk of this phase, named in advance.** *"Adding a skin requires no renderer code
change"* is a claim that can only be falsified by trying, and it will be tempting — at the third or
fourth spirit — to add one small special case rather than widen the schema. RF-079 exists to make
that falsification happen early, on a face whose correct appearance is already known: if the
procedural face cannot be expressed as a manifest, the schema is wrong while there is still time to
say so.
