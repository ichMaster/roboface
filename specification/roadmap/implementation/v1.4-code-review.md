## Finding 1 — 🔴 The device never closes its window on `asr`

**`firmware/src/main.cpp:353`**

```cpp
case roboface::ParseResult::kAsr:
    Serial.printf("\n[heard] %s\n", frame.text.c_str());
    return;
```

**Failure scenario.** A person speaks. The recogniser endpoints at ~500 ms of silence; the server
closes the window, sends `asr`, and starts the turn — exactly as RF-052 and the updated
`ARCHITECTURE.md` §Turn lifecycle describe. The device prints the transcript and **carries on
capturing and streaming** until its own 700 ms end-pause elapses, then sends `listen_stop`.

Nothing errors. The turn completes. What is lost is the entire point of the change:

- The device stays in `kListening` while the server is already replying, so the *face* shows
  listening during the reply — and DEVICE_UI's rule is that a state is expressed as a face.
- It streams ~200 ms of audio into a window the server has closed. Those frames are dropped by the
  quiet-drop path added in RF-052, so they are pure waste on a link that answers congestion by
  dropping audio.
- Half-duplex is entered late: playback can begin while the device still believes it is listening.

RF-052's acceptance criteria say *"The device closes its window on `asr`"*. The server half was
built and the device half was not, and every test still passes — the integration tests drive a
**fake** device, which has no window state of its own to leave open. This is the same shape as the
v1.3 review's note, now with the ends reversed: *a feature can be complete at both ends and absent
in the middle*, and here it is complete at one end and absent at the other.

**Proposed fix.** On `asr`, if a window is open, close it through the existing `endListening()`.
One path for closing, and the duplicate `listen_stop` it sends is exactly the case RF-052 made
idempotent.

## Finding 2 — 🔴 `/vad off` during an utterance strands the window open

**`firmware/src/main.cpp`** — the loop's VAD gate, and `AudioIo::stopMonitoring`.

```cpp
if (!active_listening) pending_vad = roboface::VadEvent::kNone;
switch (pending_vad) { ... }
```

**Failure scenario.** Someone is speaking, the window is open, and `/vad off` is typed — the exact
thing a person does when active listening is misbehaving and they want to fall back to
press-and-hold. `stopMonitoring()` clears `monitoring_`, but `listening_` is still true, so `tick`
keeps draining frames and the observer keeps producing events. The gate above then throws away
**every** VAD event, including the `kSpeechEnded` that was going to close the window.

The window never closes. The device streams audio until `MAX_UTTERANCE_BYTES` (the server ends it
with an error), and in the meantime it is stuck in `kListening` — refusing every later PTT hold,
because `canStartTurn` is false. Turning the feature off is what breaks the device.

The gate is too broad. Switching the feature off should stop it *starting* windows; it must not
strip the machine of its ability to finish the one it is in.

**Proposed fix.** Gate only `kSpeechStarted`. `kSpeechEnded` and `kDiscarded` are always honoured —
they close and clean up, and neither can create a turn.

## Finding 3 — 🟠 The capture buffer is read three times after it is handed back to the DMA

**`firmware/src/app/audio_io.cpp`** — `drainCapturedFrame`.

The order is: re-arm `capture_[completed]` with `M5.Mic.record(...)`, **then** compute the peak,
**then** run the endpointer over all 320 samples, **then** `memcpy` the frame into the pre-roll
ring, and only then send it. Every one of those reads happens while the recorder owns the buffer
and is writing the next 20 ms into it.

**Failure scenario.** The loop is late — a sprite push, a WiFi retry, a reconnect. The DMA has
already begun refilling the buffer by the time the endpointer scans it, so the zero-crossing count
and the peak are computed over a blend of two moments, and the frame copied into the pre-roll is
part old and part new. The result is a pre-roll that sounds *nearly* right, which is the failure
mode that cost a whole evening in v1.3: audio with a plausible level, a plausible frame count and
no intelligible speech.

The re-arm-first ordering is deliberate and its comment is correct — the queue should not sit one
deep while a frame is *on the wire*, because the socket send is milliseconds. But that argument
only applies to the send. The peak, the endpointer and the copy are microseconds of local work, and
v1.4 put all three inside the exposed window where previously only the peak was.

This is a real narrowing, not a rewrite: the reads move before the re-arm, the **send stays after
it**, and the queue is still topped up before the only slow operation.

> Stated plainly because the history matters: this same file was rewritten twice earlier tonight on
> the theory that this race was breaking capture, and both rewrites made a working microphone worse
> until they were reverted. The race is real but it was **not** what was breaking capture. This fix
> is therefore deliberately the smallest possible one — a reordering of four lines that strictly
> reduces exposure — and explicitly not another redesign.

## Finding 4 — 🟡 `utterance_settled` can stay set indefinitely

**`server/roboface_server/router.py`** — `Connection.utterance_settled`.

Set when the recogniser ends an utterance; cleared by the next `listen_start` or the device's
`listen_stop`. A device that does neither — it crashes, or Finding 1 leaves it confused — keeps the
flag set for the life of the connection, and every binary frame after that is dropped *silently*
instead of being reported as meaningless. The quiet drop is right for the ~20 ms it was designed
for and wrong as an indefinite state.

**Defer → v5.1 (resilience).** The correct fix is a short expiry on the flag, which wants a clock on
the connection and belongs with the other timeout work rather than being improvised here. With
Finding 1 fixed the window in practice is one or two frames.

## Finding 5 — 🟡 The pre-roll ring costs ~9.6 KB of internal RAM

**`firmware/src/app/audio_io.h`** — `pre_roll_[15][320]`.

`/mem` reports `psram found=1 size=0`, leaving ~53 KB of internal RAM with the sprite and the audio
backlog already placed. RF-049 adds ~9.6 KB to that, and RF-050's guard exercises the mic/speaker
switch where `i2s_alloc_dma_buffer` has already been observed to fail outright.

**Defer → v1 HARDEN.** This is the v1.1 PSRAM finding, and the right fix is to make PSRAM work
rather than to shave the pre-roll — trimming the ring would trade the first syllable of every
utterance for headroom that a working PSRAM would give back many times over. Flagged again here
because each phase adds to the same budget and it has now reached the audio path twice in one night.

## What's solid

- **The pure/glue split held under pressure.** Every decision v1.4 makes — when speech starts, how
  long a pre-roll is, who may listen — is in `src/pure/` and host-tested; the glue only owns
  buffers and the bus. 34 new host tests run in 15 seconds with no board attached.
- **Two measures in the endpointer, not one.** Rejecting loud sub-100 Hz rumble is not a
  hypothetical nicety: it is the exact signal that recognised as an empty string in v1.3, and an
  energy-only VAD would open a window on every occurrence of it.
- **Half-duplex resumes from one place.** Putting the resume in `releaseBus` — the single point
  every exit from playback passes through — is what makes "the device can never end up permanently
  deaf" a structural property rather than a list of cases someone remembered.
- **The mock was fixed rather than worked around.** `MockASRSession` had modelled a recogniser that
  answers before hearing anything since v1.3. It could not be noticed then; it would have made
  every v1.4 utterance end on its first frame. A mock that is wrong in a way the current code cannot
  detect is a trap set for the next version.
- **`listen_stop` idempotence is the right call.** Both ends are correct and merely noticed the
  silence at different moments; treating that as a protocol violation would put a fault on the
  screen for every hands-free turn.

## Fixes applied

### Fix 1 — the device closes its window on `asr` (finding #1)

`kAsr` now calls `endListening()` when a window is open. One path for closing a window, so the VAD
route, the PTT route and the server route cannot drift; the duplicate `listen_stop` is precisely the
case RF-052 made idempotent.

**Regression test.** `pio test -e native` cannot press a socket, so the test is on the pure
half: `test_state` gains a case asserting `kListening --kListenStopped--> kThinking` is the
transition this path uses, and `tests/contract/test_turn_lifecycle.py::
test_a_late_listen_stop_is_not_a_second_turn` already pins the server side of the duplicate. The
device-side wiring is validated by compile plus the hardware run.

**Verification.** `pytest` 501 · `pio test -e native` 219 · ruff clean · strict mypy clean. Commit `fb402cd`.

**Architecture impact.** None to the contract — `ARCHITECTURE.md` §Turn lifecycle already describes
the recogniser ending the utterance. This makes the device match what was documented, which it did
not.

### Fix 2 — switching active listening off no longer strands the window (finding #2)

The loop gates only `kSpeechStarted`. `kSpeechEnded` and `kDiscarded` are always honoured: neither
can create a turn, and both are needed to finish or clean up the one in progress.

**Regression test.** `test_vad` gains `an_utterance_can_always_be_finished`, asserting the
endpointer still reports `kSpeechEnded` for a window opened before the feature was switched off —
the pure statement of "turning it off must not remove the ability to finish".

**Verification.** `pytest` 501 · `pio test -e native` 220 · ruff clean · strict mypy clean. Commit `c3b6937`.

### Fix 3 — the cheap reads happen before the re-arm (finding #3)

`drainCapturedFrame` now computes the peak, runs the endpointer and copies into the pre-roll
**before** handing the buffer back to the recorder; the socket send — the only slow step, and the
one the re-arm-first comment was actually about — still happens after it. The queue is topped up
before the milliseconds and not before the microseconds.

**Regression test.** The ordering is not observable from the host, so this is a reasoned change with
no new test rather than a tested one, and it is recorded as such. `test_pre_roll` continues to pin
the ring's behaviour and `pio run -e cores3` its compilation.

**Verification.** `pytest` 501 · `pio test -e native` 220 · ruff clean · strict mypy clean. Commit `408c75d`.

### Final state

`pytest` 501 passed / 3 skipped · `pio test -e native` 220 · `ruff` clean · strict `mypy` clean ·
`pio run -e cores3` compiles.

## Finding 8 — 🔴 The recorder did not run on the board — FIXED

Found by testing the phase on hardware, which is the step this review said would be the one to find
something. It was four faults wearing each other's symptoms, and each was invisible from the suite.

**1. The I2S bus was still configured for output when the microphone started.** `M5.Mic.begin()`
returns true regardless, `record` accepts every buffer, and frames arrive at the right rate — but a
person shouting 20 cm from the board measured *identically to an empty room* (`p50` 8%, `max` 41%
either way). A 20 ms pause after releasing the speaker fixes it. `startSpeaking` had the same fault
in the other direction: it claimed the bus in the same breath as ending the microphone, the driver
refused (`register I2S object to platform failed`), and every reply was silence while its text still
reached the screen.

**2. The window cap fired four billion milliseconds early.** `now_ms` is read at the top of the loop
and `listen_opened_ms` stamped later in the same iteration, so their unsigned difference underflowed.
Every window closed 53 ms after opening, which produced *all* of: one frame per window, an endpointer
that never reported an end, and windows reopening without pause. Three symptoms, one subtraction.

**3. `MIC_GAIN` was set for a deaf microphone.** 64 was chosen while fault 1 was active. With the
microphone working, ordinary speech measured `p50` 84% and `p90` 99% — a square wave. Every level
meter called that an excellent signal and recognition returned nothing for it. At 20 the same speech
sits at `p50` 9%, `p90` 34%.

**4. No pre-roll.** The window opens only after 150 ms of confirmed speech, so the first syllable
never reached the recogniser: "Привіт, як справи" came back as "ЯК ВОРОРІВ ОДНЬ ЗУ й ЗАМУКАЮСЬ".

### What made the difference

Guessing at thresholds cost three reflashes and produced 6% (caught the room), 25% (missed the
voice) and 40% (caught the room again). A `/cal` command that prints the per-frame distribution
turned it into one measurement:

|  | p50 | p90 | max |
|---|---|---|---|
| silence | 3% | 3% | 4% |
| speech | 9% | 34% | 62% |
| quiet speech | 5% | 16% | 43% |

7% clears every silent frame ever measured and sits inside the working range of even quiet speech.

**The general lesson, since it cost most of a night:** on this board a subsystem reports success and
produces plausible-looking output while doing nothing useful. Frame counts, byte counts, digests and
level meters were all healthy through every one of these faults. The things that actually found them
were the energy envelope of a saved capture, a percentile distribution, and printing a duration that
was assumed rather than observed.
