## 1. 🟠 MEDIUM — the interims never leave the server

**Anchor:** `server/roboface_server/orchestrator.py` — `ListeningTurn.drain_partials`, which nothing
calls; `router.py`, which imports `Asr` and not `AsrPartial`.

**Failure scenario.** The tracker computes a partial on every recognition chunk and pushes it onto
`self._partials`. Nothing ever drains it. So:

- **The device never receives `asr_partial`.** RF-044 added the frame, RF-046 taught the firmware to
  render it, and the roadmap lists "interims out as `asr_partial`" as a task. All of that works and
  none of it is reachable, because the one line that forwards them was never written. A feature can
  be complete at both ends and absent in the middle.
- **The queue grows for the length of the utterance.** Deepgram emits interims continuously; a
  thirty-second utterance accumulates hundreds of strings that are never read. Bounded by the
  utterance cap and released when the turn ends, which is why this is MEDIUM — but it is memory held
  for no purpose at all, which is worse than memory held for a bad one.

The two are the same omission, and the second is what makes it more than cosmetic.

**Fix.** Drain the partials where audio is pushed — that is the only point that runs repeatedly
during a window — and send each as an `asr_partial` frame.

## 2. 🟡 LOW — a `listen_start` during a reply waits rather than being refused

`_stream_reply` is awaited inside the dispatch, so a `listen_start` arriving mid-reply is not
processed concurrently; it waits for the reply to finish and then opens normally. That is safe, but
it means a person who interrupts gets their window *after* the character finishes talking rather
than being told the device was busy.

Barge-in is v3.4's, and this is the shape it will have to change. **DEFER → v1.4**, where VAD makes
overlapping windows common enough to matter.

## 3. 🟡 LOW — the ASR budget conflates slow and silent

`ListeningTurn.finish` raises `asr_failed` when nothing resolves within the budget. A vendor that is
merely slow and a vendor that heard nothing at all produce the same error, and the second is not a
failure — it is silence, which the tracker already handles correctly when the stream ends cleanly.

In practice the `UtteranceEnd` backstop resolves both, so the budget is a second line of defence and
rarely reached. **DEFER → v1.4**, alongside the VAD work that will produce far more empty windows.

---

## What's solid

- **The seam encodes the latency decision.** `open() -> ASRSession` with concurrent push and read
  means no implementation can quietly reintroduce batch recognition; a `transcribe()` shape would
  have made the mistake available.
- **The phrase-hold is tested as sequences.** Thirteen tests that are event orders rather than
  values, because "has this thought finished" is not a property of any single event.
- **The URL builder is separately testable**, and one of its tests asserts the backstop is longer
  than the endpoint — a relationship that is invisible in either number alone and silently wrong if
  inverted.
- **Three latency numbers, logged separately.** The DoD is a claim about which leg is smallest; a
  single total could neither support nor refute it.

## Fixes applied

### Fix 1 — the interims are forwarded

Partials are drained where audio is pushed — the only point that runs repeatedly during a window —
and sent as `asr_partial`. Two regression tests: one asserts the frames reach the device, the other
that the session is released so the queue cannot outlive the turn.

**Verification.** 489 pytest · ruff clean · strict mypy clean.

**Architecture impact.** None to any contract, but a note worth carrying: the frame existed, the
firmware rendered it, and nothing sent it. **A feature can be complete at both ends and absent in
the middle**, and neither end's tests notice. v1.4 adds `vad` frames with the same three-part shape.

### Fix 2 — the capture read a buffer the recorder was refilling

Found on hardware, after v1.3.0 was tagged. `tick` re-armed the buffer that had just completed and
then measured and sent that same buffer, so `record` handed it to the DMA while its contents were
still being read: every frame left as a blend of two moments in time. The microphone queue is two
deep, so keeping the recorder busy while a frame is drained requires a **third** buffer — with two
there is no slot to arm that is not the one being read. The rotation moved into pure
`CaptureSlots` (five host tests); its invariant is that the slot being read is never the slot being
armed.

**Why it survived a green suite and a passing DoD check.** Nothing downstream disagreed. The frame
count was right, the byte count was right, the digest was stable, the peak was plausible and the
level meter moved. The only visible symptom was recognition returning an empty string, which is
indistinguishable from a silent room. It took plotting the **energy envelope** of a captured
utterance — dead flat where speech modulates, with all its energy below 100 Hz — to see it, and a
batch call to the vendor on a saved capture to prove the audio, not the streaming, was at fault.

### Fix 3 — capture is the resting state of the shared bus

Stopping the codec after every window and starting it again for the next is churn the capture
faults came out of — a restart that reports success while the port is still held for output. The
microphone is now left running between windows; the speaker takes the bus only when output needs it.

### Fix 4 — `listen.stop` reports RMS, not just peak

Peak was **actively misleading**: a capture at 99% peak recognised fine, one at 19% peak recognised
as nothing at all, and acting on peak led to a microphone gain that made recognition *worse*. RMS
predicts recognition (≈ −20 dBFS transcribes, ≈ −34 dBFS does not); peak stays for the one thing RMS
cannot see, which is clipping.

### Fix 5 — an empty utterance no longer strands the device

v1.3 removed the firmware's own turn-ender because a reply now follows an utterance. When
recognition returns nothing there is no reply, so nothing closed the turn: the device sat in
`thinking` and refused every later hold, which presents as a broken microphone. The server now
closes the turn with an empty terminal reply.

### Fix 6 — the level meter was starving the microphone

Marking the sprite dirty every loop made the 33 ms repaint cap fire constantly, and a full 153 KB
push at 30 Hz left the loop unable to service the microphone within its 40 ms of buffering: capture
returned 47% of every window at any window length. Ten repaints a second looks identical and
returns 97%.

## Still open — the phase DoD is not met

**RF-047 stays open.** The end-to-end voice loop does not yet produce a transcript from the board.
What is established, and what is not:

| Leg | State |
|---|---|
| Device → server framing | **Good** — 97% of every window arrives, real-time paced |
| Server → Deepgram streaming | **Good** — full audio delivered (`queued == sent`), fed at 1× |
| Deepgram request parameters | **Good** — a saved capture transcribes at 0.854 confidence |
| Device capture content | **Bad** — flat, sub-100 Hz, no voice band, at every gain tested |

The vendor and the server are exonerated by direct evidence: the same bytes the server sends were
saved and transcribed correctly by the batch API, and a standalone stream of that file at 1× pacing
returned the full sentence (**faster than real time returns nothing** — worth remembering, it is not
documented anywhere obvious). The remaining fault is in what the microphone hands the firmware.

Ruled out on hardware: sample rate and framing, byte order, de-interleaving and rate re-labelling,
DC offset, level (amplification does not recover it), magnification (16/24/64 scale the same rubbish
proportionally), the request's `channels`/`smart_format` parameters, and the two faults fixed above.

**Not yet tried, in order:** a loopback listen-then-play to establish by ear whether the microphone
hears the room at all; `M5.Mic.record` against a single large time-confirmed buffer as the reference
project does, rather than per-frame slots; and the `internal_mic` config path, whose test run did not
capture.
