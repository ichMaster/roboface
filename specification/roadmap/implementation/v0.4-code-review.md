## Findings

### 1. 🟠 MEDIUM — The whole sprite is pushed every loop

**Where:** [`main.cpp`](../../../firmware/src/main.cpp) `loop()` — `chrome_view.draw(...)` followed by
`renderer.push()`, unconditionally, with `delay(5)` at the bottom.

**The arithmetic**, on the real numbers:

```
sprite frame        153,600 bytes   (320 x 240 x 16-bit)
intended loop rate      200 Hz      (delay(5))
implied SPI load       30.7 MB/s
Core S3 panel SPI      ~5 MB/s usable at ~40 MHz
```

**Failure scenario.** The loop cannot run at the rate it asks for; it runs at whatever the panel can
absorb, and **the push becomes the loop**. Everything else in `loop()` — `ws.loop()` servicing the
WebSocket, `net.loop()` supervising WiFi, draining the serial buffer — is then serviced at the
panel's pace rather than the network's. On a board that must notice a `reply` delta promptly (v0.2's
whole property) and will carry streaming PCM in v1, spending the entire loop repainting an unchanged
screen is the wrong trade, and it gets worse exactly when the device is busiest.

Nothing on this screen changes faster than DEVICE_UI's fastest documented transition, the **120 ms**
chrome fade — about 8 Hz. Even 30 Hz, which is generous for a face that is currently static, costs
4.6 MB/s.

**Not measured on the board**, and said plainly: the figures above are arithmetic, not a profile.
What is observable is that the code asks for 200 Hz and the hardware cannot supply it.

**Proposed fix.** Push at a bounded rate, and only when something actually changed — a state
transition, a chrome visibility change, or a fade in progress. The face is redrawn on change
already; the push should follow the same discipline.

### 2. 🟠 MEDIUM — Battery and charge are read over I²C every loop

**Where:** `main.cpp` `updateChrome()` — `M5.Power.getBatteryLevel()` and `M5.Power.isCharging()`,
called from the loop body.

**Failure scenario.** Both talk to the AXP2101 over I²C. At the loop's intended 200 Hz that is ~400
I²C transactions a second for a value that changes on the scale of minutes. It burns bus time the
touch controller (v2.4) and the IMU (v2) will want, and it burns it continuously — a device sitting
idle on a desk is doing it forever.

Battery percentage is not a fast-moving fact. DEVICE_UI even says charge is *"otherwise expressed as
the face's own tiredness"* rather than as a number, which is the opposite of something worth polling
at audio rates.

**Proposed fix.** Read power on a timer — a second or two is far finer than the quantity moves — and
keep the last value between reads.

### 3. 🟡 LOW — The self-test writes `state` directly — DEFER → v2.1

`stepSelfTest()` assigns to `state` rather than going through `transition()`, so during the cycle the
state variable is not the device's state — it is a display request. It is restored afterwards (and a
bug where it was *not* was found and fixed during RF-022), and the alternative — synthesising events
to walk the machine into `error` — would be worse, since the machine correctly refuses several of
those transitions. Worth revisiting in v2.1 when the renderer gains its own animation clock and a
"show this face" path independent of device state becomes natural.

### 4. 🟡 LOW — One frame of stale chrome on a state change — DEFER → v2.1

`apply()` calls `render()`, which draws chrome from the `Chrome` model as it stood at the **previous**
loop iteration; the loop then updates and redraws it. So a state change briefly shows chrome that is
one frame old. At the current push rate that frame is imperceptible, and fixing it properly means
deciding whether `render()` owns the chrome update or the loop does — a small design question rather
than a defect. It becomes visible only if the push rate drops a long way, which finding 1's fix does
not do.

## What's solid

- **The pure/glue line held under pressure.** The two host-tested modules carry 24 of this version's
  35 new tests, and the geometry rule "never block the face" ended up as a `static_assert` in the
  module that could violate it — a compile error rather than a visual judgement.
- **A bug was caught in review before it shipped**: `chrome_view` drew invented facts (`kConnected`,
  `0%`) because `Chrome` exposed none. It would have looked entirely plausible on a screen.
- **A second was caught by reading the serial output of a real run**: the self-test claimed *"back to
  the real state"* and left the device in `error`.
- **The distinctness test has headroom rather than only just passing**, which is what stops a future
  tweak to a recipe silently making two faces indistinguishable.
- **The DoD's visual clause was actually checked** — six distinct faces, no tearing, confirmed on the
  board — rather than asserted from the code.
