## 1. 🟠 MEDIUM — a failed phrase leaks its TTS stream

**Anchor:** `server/roboface_server/orchestrator.py`, `_speak`.

**Failure scenario.** `_speak` opens `self.tts.synthesize(phrase)` and raises `ProviderError` on
three paths — the first-audio timeout, a `ProviderError` from the vendor, and a mid-phrase failure.
None of them close the iterator. In the real adapter that iterator owns an `httpx` streaming
response and its connection, so **every failed phrase leaks one**. A turn with several phrases can
leak several; a vendor having a bad minute leaks one per attempt until the pool is exhausted, and
the symptom then is `tts_failed` on turns whose synthesis would have worked.

This is the same defect v0.2's review closed for the LLM stream, where `_close_quietly` was added
for exactly this reason. The second provider reintroduced it because `_speak` was written as a
generator and generators feel like they clean up after themselves — they do, but only when the
consumer is what stops them, and here the producer is what raises.

**Fix.** Close the stream on the way out, with the existing `_close_quietly`, on every path that
leaves `_speak` early.

## 2. 🟠 MEDIUM — `write` claims to have accepted audio it threw away

**Anchor:** `firmware/src/app/audio_io.cpp`, `AudioIo::write`.

```cpp
if (!backlog_.attached()) return length;   // nowhere to put it; drop rather than crash
```

**Failure scenario.** Returning `length` means "I accepted all of it". Nothing did. This is exactly
how the phase's hardest bug hid: PSRAM reported zero free, the ring never attached, and the device
sat silent while the server logged hundreds of chunks sent and the board's own counters read
`buf=0 q=0`. There was no error anywhere, because every layer had been told the audio was fine.

Reporting zero — the truth — makes the caller's backpressure path handle it, and makes the counters
say what is happening.

**Fix.** Return 0 when there is nowhere to put the data, and count it, so a device that cannot
allocate says so continuously rather than once at boot.

## 3. 🟠 MEDIUM — PSRAM reports zero free on this board

**Anchor:** `firmware/platformio.ini` (`board_build.arduino.memory_type = qio_opi`,
`-DBOARD_HAS_PSRAM`), observed at runtime: `[audio] backlog 48 KB (psram free 0 KB, internal free
57 KB)`.

**Failure scenario.** `heap_caps_malloc(…, MALLOC_CAP_SPIRAM)` returns null and `ESP.getFreePsram()`
is 0, despite the board being a Core S3 with 8 MB of octal PSRAM and the build declaring both the
memory type and the capability flag. Audio therefore runs on a 48 KB internal fallback, which works
— the speaker paces the backlog and TCP paces the socket — but it is a fifth of the intended buffer
and it competes with the network stack for internal RAM.

**Why it matters more later than now.** CLAUDE.md and ARCHITECTURE both assign PSRAM to the audio
buffers, **the face framebuffer and the JPEG frames**. v2's animated renderer and v3's camera path
are sized on the assumption that PSRAM exists. A 320×240×16 sprite is 153 KB; v3's JPEG buffers are
larger again. Discovering this in v3, with a camera to debug at the same time, would be far more
expensive than resolving it now.

**Why deferred rather than fixed here.** The fix is a build-configuration investigation — memory
type, flash mode, and whether M5Unified's own init claims it — not a code change in this phase's
scope, and v1.1's DoD passes without it. **DEFER → v3.1**, with the note that the end-of-phase
HARDEN sweep may reasonably pull it forward, since the cost of the investigation does not grow but
the cost of being wrong about it does.

## 4. 🟡 LOW — binary frames bypass the device's inbound size cap

`Ws::handleText` refuses a frame over `kMaxInboundFrameBytes` before parsing it, which was v0.3's
review finding. `WStype_BIN` has no such check: the payload goes straight to the binary handler. In
practice the ring bounds what is stored and the WS library has already buffered the frame by then,
so the exposure is smaller than it looks — but the asymmetry is unintentional, and v1.2's capture
path will add a second binary direction. **DEFER → v1.2**, where the binary paths are being touched
anyway.

## 5. 🟡 LOW — the refusal path is unexercised on hardware

`chunksRefused` reads 0 across every observed turn, including a 429 KB reply. `playRaw` evidently
waits for a slot far more often than it refuses, so `PcmRing::unread` — written specifically for the
refusal case, and host-tested — never runs on the device. It is correct and cheap, and the case it
covers is real in principle; but "tested only in tests" is worth recording rather than assuming.
**DEFER — documented.**

## What's solid

- **The interleaving is asserted, not hoped for.** `test_audio_starts_before_the_model_finishes_writing`
  compares the first audio's position against the last delta's, which is the same comparison the
  hardware check makes from the logs. The hardware run *confirmed* the property rather than
  discovering it.
- **The splitter's rule earns its complexity.** Boundary-plus-whitespace makes "not yet" a distinct
  answer from "no", and that single distinction is what stops `3.5` becoming two spoken phrases.
- **Sample alignment is guarded on both sides** — the adapter realigns what the transport splits,
  and the ring hands out whole samples only. Either alone would have left a way to shift a phrase
  by a byte.
- **The speaking window closes on every exit path**, including an aborted turn, which is what keeps
  the shared I2S bus available to v1.2.

## What the hardware found

Four faults, none reachable from a host test, each of which sounded like a different problem than it
was. They are recorded here because each is a fact about this stack rather than a mistake in this
phase alone.

| Symptom | Actual cause |
|---|---|
| Silence, while the server logged hundreds of chunks sent | PSRAM zero free → ring never attached → `write` discarded everything and said it had not |
| "The beginning is good and then the sound breaks up" | `playRaw` **drops** a chunk when both slots are claimed; it does not wait. The network outruns 16 kHz within a second |
| Distortion | `playRaw` keeps the pointer rather than copying, and was handed a stack buffer; channel −1 also let consecutive chunks sound *together* rather than queue |
| Speaker held the I2S bus for the rest of the session | `ws.cpp` whitelists which `ParseResult`s become a frame event, and `kTtsEnd` was not on the list — discarded one layer below `main.cpp` |

The last is the one to remember: **a new `ParseResult` must be added to `ws.cpp`'s dispatch as well
as to the parser**, or it is dropped silently in a layer nobody is looking at.

## Fixes applied

### Fix 1 — a failed phrase closes its stream — `17a02de`

**Change.** `_speak` wraps its whole body in `try/finally` and closes the iterator through the
existing `_close_quietly`, which now takes `AsyncIterator[Any]` since both the LLM's `str` deltas
and TTS's `bytes` chunks pass through it.

**Regression test.** Three, using a provider double that counts opens against closes — on a
mid-phrase failure, on a first-audio timeout, and on a successful multi-phrase turn. The leak is
invisible to every other assertion: the audio is right, the error code is right, and a connection
stays open.

**Verification.** 432 pytest · ruff clean · strict mypy clean.

**Architecture impact.** None to any contract. One note for the next provider seam (`ASRProvider`,
v1.3): **a provider stream must be closed by whoever opened it, on every path out**. A generator
cleans up when its *consumer* stops it, which is why this looked safe and was not — here the
producer raises, and the consumer never sees the iterator again.

### Fix 2 — the device reports what it actually accepted — `9850828`

**Change.** `AudioIo::write` returns 0 rather than `length` when the backlog never attached, and
counts the dropped bytes. The status line carries `drop=`, so a mute device states its reason
continuously rather than once at boot.

**Regression test.** None possible on the host — this is glue whose failure mode is an unallocated
PSRAM buffer. The guard is the counter itself: the condition that hid for an entire debugging
session is now reported on every status line, which is the check.

**Verification.** `pio run -e cores3` SUCCESS · 147 host tests · observed on hardware.

**Architecture impact.** None. A device-level convention worth carrying: **a buffer that cannot
store must not report that it did.** v1.2's capture path has the same shape in the opposite
direction.

### Finding 3 — held by the v1 HARDEN sweep

The sweep attempted this and **could not land it**, so it is held rather than forced, with what was
learned so the next attempt does not start from nothing.

**Attempted.** `board_build.psram_type = opi` added alongside the existing
`board_build.arduino.memory_type = qio_opi` and the board's own `-DBOARD_HAS_PSRAM`. Full rebuild,
flashed, boot line re-read:

```
[audio] backlog 48 KB (psram free 0 KB, internal free 57 KB), volume 120
```

No change. The setting was reverted rather than left in place: an ineffective configuration line
reads as a solved problem to the next person.

**What is now known.** The Core S3 board definition (`m5stack-cores3.json`) declares
`-DBOARD_HAS_PSRAM` and `flash_mode: qio` but sets **no** `psram_type` or `memory_type` of its own;
`maximum_ram_size` is 327680, which is internal RAM only. `ESP.getFreePsram()` returns 0 and
`heap_caps_malloc(…, MALLOC_CAP_SPIRAM)` returns null at runtime.

**Where to look next**, roughly in order of cost:

1. Whether the **bootloader** actually got rebuilt for the octal configuration — `memory_type`
   selects precompiled artefacts, and a bootloader that did not initialise OPI PSRAM would produce
   exactly this: the flags are right, the hardware is right, and the memory is never mapped.
2. Whether `M5.begin()` claims or reconfigures PSRAM before `setup()` runs.
3. A minimal sketch — `psramInit()` plus `ESP.getPsramSize()` and nothing else — to separate a board
   or unit problem from this firmware's configuration.

**Why holding is safe for now.** Audio works on the internal fallback: the speaker paces the backlog
and TCP paces the socket, so a smaller buffer costs throttling rather than correctness, and the DoD
passed with it. **What is not safe is reaching v3 with this open** — the camera path's JPEG buffers
and v2's animated renderer are both sized on PSRAM existing, and diagnosing this alongside a camera
would be far more expensive than diagnosing it alone.
