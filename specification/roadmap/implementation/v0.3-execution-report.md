## What the phase delivered

The two-layer split ARCHITECTURE §Firmware architecture specifies, enforced rather than intended:
the `native` environment compiles **only** `src/pure/`, so an `#include <M5Unified.h>` reaching pure
code fails the host build. That was verified by deliberately doing it.

Everything that can be wrong lives in the tested half -- the wire codec, the state machine, backoff,
the line reader, the URL parser -- and `app/` is wiring. 61 host tests run on a laptop with no board
attached.

## Four bugs the tests and the hardware found

1. **The state machine claimed `idle` while unable to reach the server** (RF-014). `wifi_connecting`
   exited on `wifi_up` rather than `socket_up`, so a device whose link had returned but whose socket
   had not would invite a person to type into nothing -- during precisely the window a reconnect
   spends most of its time in. Found by the exhaustive transition test; the machine was changed, not
   the test.
2. **The two environments compiled the same headers under different C++ standards** (RF-015). Host
   at 17, board at 11, because the ESP32 core appends its own `-std=gnu++11` and won. While that
   stood, "host-tested" did not mean the code that ships. Now unset in `platformio.ini`, with a
   `static_assert` that fails in whichever environment loses C++17.
3. **The URL parser accepted `:0` and `:70000`** (RF-016). Both silently became a `uint16` nobody
   would notice -- a connection to port 0 or a wrapped-around number, retried forever. Found by
   moving `parseWsUrl` out of `app/ws.cpp` into `pure/`, which was itself a layering fix: parsing
   behind an `M5` include is what CLAUDE.md's firmware rule exists to forbid.
4. **`Serial` was writing to the UART pins, not USB** (RF-017). The Core S3's USB-C is the chip's
   *native* USB, and `Serial` defaults to GPIO43/44 -- so the debug channel, which is **v0.3's only
   turn source**, was silent while the board ran perfectly. No host test could have found this;
   only flashing it could.

## The DoD, and what remains

Roadmap §v0.3: *"on the real board, typing a line over serial produces the model's reply over serial;
pulling WiFi moves the device to `offline` and it reconnects on its own; `pio test -e native` passes
and `pio run -e cores3` compiles clean."*

| Clause | Status |
|---|---|
| `pio test -e native` passes | ✅ 61 tests |
| `pio run -e cores3` compiles clean | ✅ RAM 15.1%, flash 16.5% |
| a typed line returns the model's reply | ⏳ **blocked by the host firewall** -- see below |
| pulling WiFi -> `offline` -> reconnects | ⏳ partly shown; needs the clause above first |

Observed on the board:

```
[net] up, ip 192.168.1.131
[state] wifi_connecting
[ws] server 192.168.1.64:8000/ws
[ws] reconnecting in 427 / 774 / 1842 / 3551 / 6640 / 13256 ms
[status] wifi_connecting · link up 192.168.1.131 · ws disconnected · up 30s
```

WiFi association, the URL parser, the state machine and the backoff all work on hardware. The
backoff's growth-with-jitter is the behaviour RF-014 tested on a host, seen on a device. The state
machine holding `wifi_connecting` rather than claiming `idle` is bug 1 above, fixed and confirmed.

**Why the turn is not verified.** The macOS Application Firewall drops inbound connections to the
Python **app bundle** -- `…/Python.app/Contents/MacOS/Python`, not `bin/python3.14`, which is why
allowing the latter changed nothing. The server logged **zero** connection attempts while the board
retried to its 30 s ceiling. The Mac can ping the board and the server is bound to `*:8000`: the
board is behaving correctly and the host is refusing it. This is a host configuration fact, not a
defect in anything this phase built.

To close it:

```bash
PYAPP=$(lsof -p $(lsof -ti tcp:8000) | awk 'NR==2{print $NF}')
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add "$PYAPP" --unblockapp "$PYAPP"
```

Then `pio device monitor` and type a line.

## Architecture impact -- for the next reconcile

1. **The transport is `ws://`, not `wss://`** (RF-016). ARCHITECTURE §Contracts now records it and
   why: the server runs uvicorn with no TLS, the firmware keeps the scheme in `config.h`, and closing
   the gap is that line plus a certificate. **This is the phase's one open specification question.**
2. **`/tools` and `/firmware` are in the repo layout**; the firmware's pure/glue split is enforced by
   the `native` build filter, not by convention.
3. **The firmware mirrors the wire contract** in `pure/ws_protocol.h`, and
   `tests/contract/test_firmware_mirror.py` compares the two languages in the **Python** CI job --
   so drift is caught by someone who never runs `pio`.
