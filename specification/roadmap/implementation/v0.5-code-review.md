## 1. 🔴 HIGH — `/chat-off` reverts the device to a state that is no longer true

**Anchor:** `firmware/src/main.cpp`, the `/chat-off` handler; `firmware/src/pure/console.h`.

**Failure scenario.** `/chat-on` while the device is `idle`. The console is open; WiFi drops. The
state machine keeps running underneath — `apply(kSocketLost)` is called unconditionally — so `state`
becomes `offline` and chrome's link indicator goes dark. Now `/chat-off`:

```cpp
state = console.savedState();   // idle, captured at /chat-on
```

The device is put back to `idle` with no socket. **The panel shows the idle face while the link is
down**, and it stays that way until the next transition happens to correct it. MISSION's rule is
that a device state is a face; a face that asserts a state the device is not in is the same class of
defect v0.4's review fixed for the self-test, arrived at from the opposite direction.

**Root cause — the analogy with `/faces` was wrong.** The self-test *drives* state: it assigns
each of the six in turn, so it must put the real one back. The console does **not** drive state at
all; it only borrows the screen while the state machine carries on. Saving and restoring is
therefore not merely unnecessary, it actively reverts legitimate transitions.

**Fix.** The console borrows the *screen*, not the *state*. `/chat-off` stops drawing the transcript
and re-renders whatever state the device is genuinely in. In the ordinary case — nothing changed
during the session — that is the same face that was showing before, so the DoD's intent is met; in
the case above it shows `offline`, which is the truth.

## 2. 🟠 MEDIUM — the console font leaks into chrome and the debug line

**Anchor:** `firmware/src/app/console_view.cpp` (`canvas->setFont(&kConsoleFont)`);
`firmware/src/app/chrome_view.cpp:105`; `firmware/src/main.cpp` (the debug line).

**Failure scenario.** `ConsoleView::draw` sets the 10×20 U8g2 face and never puts anything back.
**No other module sets a font at all** — chrome's fault line and the debug line only call
`setTextSize(1)` and inherit whatever is current. So the moment the console has drawn once, every
later `drawString` on that canvas uses a 20 px Cyrillic face instead of the default. The fault code
lives in a 28 px band, so a 20 px face plus its ascent is close to overflowing it, and the debug
line at (4, 4) is drawn far larger than intended. This outlives `/chat-off` — the sprite keeps the
font — so the damage is not confined to the console.

**Fix.** Every drawer sets the font it needs, rather than inheriting one. `ConsoleView` sets the
console face; `ChromeView` and the debug line set the built-in `Font0` they were written against.
Inheriting a font across drawers is what made this reach beyond the module that caused it.

## 3. 🟠 MEDIUM — the console and the self-test both borrow the screen, with separate saved states

**Anchor:** `firmware/src/main.cpp`, `/chat-on` handler vs `startSelfTest` / `stepSelfTest`.

**Failure scenario.** `/faces` starts cycling; mid-cycle, `/chat-on`. Now `self_test_running` is
true *and* the console is on. `stepSelfTest` keeps assigning `state` (so `console.savedState()`
captured a self-test state — `thinking`, say — rather than a real one), while `render()` draws the
transcript, so the self-test's whole purpose (look at the six faces) silently does nothing. When the
cycle ends it restores `self_test_saved_state` and calls `render()`, which draws the console again.

Two independent borrowers of one screen, each with its own idea of what to give back.

**Fix.** `/chat-on` refuses while the self-test is running, and says so — the same shape as the
existing `[busy] self-test running — line ignored` guard the text path already has. One borrower at
a time.

## 4. 🟠 MEDIUM — the reply is re-wrapped on every repaint

**Anchor:** `firmware/src/app/console_view.cpp` → `transcript.replyLines()` → `wrapUtf8`.

**Failure scenario.** `replyLines()` wraps the **entire** accumulated reply and then discards all
but the last 9 lines. The buffer is capped at 2048 bytes, so at 26 columns that is up to ~79 wrapped
lines — ~79 `std::string` allocations — built and thrown away on every repaint. While a reply
streams, repaints run at the 33 ms cap, so roughly 2400 short-lived allocations a second, on a
device whose heap is not compacted.

**Why deferred rather than fixed now.** It is waste, not a defect: the buffer is bounded, the
repaints are bursty (they stop when the reply ends), and the DoD passed on hardware with a long
Ukrainian answer. The right fix is a cached wrap invalidated on append, which is a small change —
but its value is structural rather than immediate, and it becomes structural in **v2.1**, where the
renderer repaints continuously for the idle animation instead of only while text arrives. Fixing it
there, against a renderer that actually runs every frame, is fixing it where it can be measured.

## 5. 🟡 LOW — no prompt after an error frame

`printConsolePrompt()` is called on the reply-final path but not on the `kError` path, so a turn
that fails leaves the console with no `chat>` and it reads as hung. Cosmetic; the next line typed
still works. **DEFER → v5.1** (resilience and error presentation).

## 6. 🟡 LOW — the transcript accumulates while the console is off

`transcript.startTurn` / `appendReply` run regardless of whether the console is on, so every turn
pays a little UTF-8 work nobody looks at. It is bounded and small, and it means the transcript is
already warm if the console is opened. `/chat-on` clears it anyway. **DEFER — documented, harmless.**

## What's solid

- **The pure/glue split held.** Everything that could be tested on a laptop was: wrapping, the
  in-flight character, the bound, the mode's save/restore, the grid arithmetic. The three findings
  above are all in the glue — the layer where the split predicts defects will be.
- **The UTF-8 handling is right.** The equivalence test (split a reply at *every* byte offset,
  compare to appending it whole) is the strongest assertion in the phase, and it covers the failure
  everyone hits with streamed multi-byte text.
- **Coverage was verified, not assumed.** Decoding the font's own glyph table — and landing on
  exactly the 387 glyphs the file declares — is why the DoD passed first time instead of discovering
  a missing `ґ` on the panel.
- **The repaint discipline was respected.** A delta marks the sprite dirty; the existing 33 ms cap
  decides when to paint. v0.4's fix was extended rather than undone.

## Fixes applied

### Fix 1 — the console borrows the screen, not the state — `dbf7c01`

**Change.** `/chat-off` no longer assigns `state`; it renders whatever state the device is in.
`ConsoleMode` loses `savedState()` entirely and keeps only the idempotent on/off, which is all
screen-borrowing needs.

**Regression test.** `test_console` was rewritten: the save/restore cases are gone, because the
behaviour they pinned was the defect. What remains asserts idempotence in both directions. The
property that replaced them — "leaving shows the current state" — lives in `main.cpp`'s render path
rather than in a pure type, and is checked on hardware.

**Verification.** 131 host tests, `pio run -e cores3` green, flashed. `/chat-off` now reports
`console off — showing wifi_connecting`, naming the state the device is actually in rather than the
one captured on entry.

**Architecture impact.** The console's contract changed from *"restores the face and state that were
showing before"* to *"stops drawing the transcript; the face returns to the device's current
state"*. In the ordinary case these are the same thing, which is why the DoD reads the same. They
differ exactly when a transition happened while the console was open, and there the new behaviour is
the correct one. **Roadmap §v0.5's DoD wording should be read this way**, and any later feature that
borrows the screen (v2.6's skin carousel is the obvious candidate) should borrow the screen only —
the `/faces` self-test is the exception, because it is the one thing that genuinely drives state.

### Fix 2 — each drawer sets its own font — `1b78850`

**Change.** `ChromeView::draw` and the corner debug line set `fonts::Font0` explicitly.
`ConsoleView` already set its own.

**Regression test.** None possible: a font is M5GFX canvas state with no pure surface to assert
against. The check is the on-device DoD re-run — the fault line and the debug line are read *after*
the console has drawn, which is the condition that produced the defect.

**Verification.** Compiles; flashed; chrome renders normally after a console session.

### Fix 3 — one borrower of the screen at a time — `6c1ec75`

**Change.** `/chat-on` refuses while `self_test_running`, in the same shape as the existing `[busy]`
guard on the text path.

**Regression test.** Hardware: `/faces` then `/chat-on` two seconds later now prints
`[busy] self-test running — /chat-on ignored` and the cycle continues undisturbed.

**Verification.** 131 host tests, compile, and the hardware check above.
