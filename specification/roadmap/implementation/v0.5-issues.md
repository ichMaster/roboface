# v0.5 — GitHub Issues

Issues for phase **v0.5 — Serial chat console** (version **v0 — Skeleton**),
derived from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§v0.5) and the
contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md) (§The face, §Interaction, §Repo layout).
This file is scoped to a single phase; IDs continue from the previous phase
(RF-022 → **RF-023…RF-027**).

v0.4 closed the skeleton, but the screen can show a turn's *state* and not its *content*: a reply is
only readable over the serial cable. This phase adds a console mode that borrows the screen for the
transcript, the way the `/faces` self-test already borrows it. No seam changes — the WS protocol,
`EmotionFrame`, the provider seams and `IFaceRenderer` are all untouched; the transcript is drawn into
the sprite `StubRenderer` already owns, alongside chrome. The one genuinely new capability is Cyrillic
on the panel, because the product answers in Ukrainian and M5GFX bundles no Cyrillic font.

## v0.5 — Serial chat console

### RF-023 — `pure/transcript.h` — UTF-8-safe wrapping and a bounded transcript

**Description:**
The pure half of the console: turning a stream of reply deltas into a bounded set of screen lines.
Touches `firmware/src/pure/` and `firmware/test/` only — header-only, `namespace roboface`, no
Arduino include, so it is host-tested under `pio test -e native`.

**What needs to be done:**
- `wrapUtf8(text, columns)` — word-wrap counting **codepoints, not bytes**. Ukrainian is two bytes per
  letter, so a byte-based wrap would both mis-measure every line and cut a character in half, which
  renders as a replacement glyph rather than as a wrong line break.
- A word longer than a line is hard-broken, and the break lands on a codepoint boundary.
- A `Transcript` type holding the outgoing message and the accumulating reply, capped at N lines and
  N bytes so a long reply cannot grow the buffer without bound on a device with finite PSRAM.
- **Deltas are fragments, not lines.** A `reply` frame carries whatever the model emitted — often a
  partial word. The transcript must append into the text and re-wrap, never wrap each delta on its
  own, or every fragment boundary becomes a spurious line break.
- Total behaviour over the awkward inputs: empty, whitespace only, a single word longer than a line,
  mixed Latin and Cyrillic, and a truncated UTF-8 sequence at the end of a delta (which is what a
  split multi-byte character looks like arriving over the wire).

**Dependencies:** None

**Expected result:**
A header-only module that turns an appended stream of UTF-8 fragments into at most N wrapped lines,
proven by host tests without a board.

**Acceptance criteria:**
- [ ] `wrapUtf8` never emits a line whose byte sequence splits a UTF-8 character
- [ ] A word longer than `columns` is hard-broken at a codepoint boundary rather than dropped or overrun
- [ ] Appending a reply in fragments produces the same lines as appending it whole
- [ ] The transcript is bounded: an arbitrarily long reply keeps the last N lines and never grows
- [ ] **Unit test:** the above, in `firmware/test/test_transcript/`, green under `pio test -e native`
- [ ] No `<M5Unified.h>`/`<Arduino.h>` reachable from the header — the `native` env proves it
- [ ] Ties to the phase DoD: "no mojibake, no half-characters at a line break"

### RF-024 — A Cyrillic font for the panel

**Description:**
M5GFX bundles no Cyrillic font — its `efont` set is JA/CN/KR/TW and the built-in `Font0` is ASCII —
so a Ukrainian reply would render as boxes. It does accept **U8g2 font arrays** via `lgfx::U8g2font`,
which is the mechanism its own bundled fonts already use, and it decodes UTF-8 when drawing. Touches
`firmware/src/app/` and `firmware/test/`.

**What needs to be done:**
- Choose a Cyrillic-capable U8g2 bitmap font and embed its array under `firmware/src/app/fonts/`, with
  a header comment recording its name, source and licence.
- **The licence must be compatible with this repository (MIT).** Unifont has the widest coverage and is
  GPL-licensed, so it is not eligible whatever its coverage; prefer an X11/BSD/MIT-derived font.
- Wrap it in `lgfx::U8g2font` and expose the advance width and line height as constants.
- Publish the column count the face area affords (`kFaceWidth / advance`) so RF-023's wrap and the
  renderer agree on one number rather than each computing its own.
- Verify the glyph coverage actually includes the Ukrainian letters that are not in Russian —
  **і, ї, є, ґ** — which a font advertised as "Cyrillic" can omit.

**Dependencies:** None

**Expected result:**
A licence-clean Cyrillic font compiled into the firmware, with the metrics the transcript layout needs.

**Acceptance criteria:**
- [ ] `pio run -e cores3` compiles with the font linked, and the flash cost is recorded in the issue
- [ ] The font's licence is recorded in the file and is MIT-compatible
- [ ] Coverage includes і, ї, є, ґ as well as the common Cyrillic range and ASCII
- [ ] **Unit test:** the published column constant agrees with `kFaceWidth` and the advance width, in
      `firmware/test/`, so the two halves cannot drift apart silently
- [ ] Ties to the phase DoD: "a Ukrainian reply is legible on the panel"

### RF-025 — Console mode — `/chat-on`, `/chat-off`, and the state it gives back

**Description:**
The mode switch and its serial half. Touches `firmware/src/main.cpp` and `firmware/src/pure/`.
The screen work is RF-026; this issue is the command, the prompt and the state discipline.

**What needs to be done:**
- `/chat-on` and `/chat-off` in the existing serial dispatch, both listed by `/help`, and both drivable
  from `tools/board.py --send` since that path is the same one typing uses.
- `/chat-on` announces the mode on serial and prints a prompt for the message to send; `/chat-off`
  announces leaving it.
- **Save and restore the device state**, following the `/faces` self-test precedent
  (`self_test_saved_state`): the mode must hand back the state that was showing when it started, or
  the status line and the screen disagree from then on — the exact bug v0.4's self-test already had
  to fix.
- Entering the mode twice, or leaving it when it is off, are both no-ops rather than state corruption.
- Plain typed text still sends as a turn exactly as it does today; the mode changes what is *shown*,
  not what is *sent*, so the existing "reply outside a turn" guard keeps working unchanged.
- The mode survives a WS reconnect — the socket dropping must not silently leave the console on with a
  dead link, nor turn it off behind the user's back.
- The toggle's save/restore logic is pure and host-tested; only the command parsing and printing are glue.

**Dependencies:** RF-023

**Expected result:**
A console mode that can be entered and left from serial, always giving back the state it borrowed.

**Acceptance criteria:**
- [ ] `/chat-on` prints the mode banner and a prompt; `/chat-off` restores the previous device state
- [ ] Double `/chat-on` and a stray `/chat-off` are no-ops
- [ ] `/help` lists both, and `tools/board.py --send /chat-on` works
- [ ] A WS reconnect while the mode is on leaves the mode on and the state consistent
- [ ] **Unit test:** the toggle's save/restore is total over the state enum, in `firmware/test/`
- [ ] Ties to the phase DoD: "`/chat-off` restores exactly the face and state that were showing before"

### RF-026 — The transcript on the screen

**Description:**
The join: while the console is on, the screen shows the conversation instead of the face. Touches
`firmware/src/app/` and `firmware/src/main.cpp`. Drawn into the full-screen sprite `StubRenderer`
already owns, so the transcript and chrome are pushed together and cannot tear against each other.

**What needs to be done:**
- Draw the outgoing message and the reply into the sprite, inside the face's 264×184 area — reuse
  `roboface::insideFace`/`clearOfFace` rather than restating the geometry.
- The outgoing message is visually distinct from the reply, without either being labelled in words.
- The reply grows as its deltas arrive.
- **Respect the existing repaint discipline.** v0.4's review capped pushes at `kMinPushIntervalMs`
  (33 ms) and gated them on `needs_push`; deltas arrive faster than that, so the transcript marks the
  sprite dirty and lets the existing rate limit decide when to push. Pushing per delta would put the
  loop back to being one long sprite push, which is what that fix removed.
- Chrome keeps its bands and its fade rules unchanged — link and battery are facts, and a console that
  hid them would hide a dropped link exactly when it matters.
- A reply longer than the area truncates or scrolls **deliberately**, per RF-023's bound, and never
  overruns into the chrome bands.

**Dependencies:** RF-023, RF-024, RF-025

**Expected result:**
With the console on, a question and its streaming answer are readable on the panel; with it off, the
face is back and nothing about the normal screen has changed.

**Acceptance criteria:**
- [ ] The message and the streaming reply appear on the panel while the mode is on
- [ ] Text stays within the face area; the chrome bands are never drawn into
- [ ] Pushes stay rate-limited — no push per delta
- [ ] `/chat-off` restores the face with no visual residue of the transcript
- [ ] **Unit test:** the layout maths (lines that fit, where they start) is pure and host-tested; the
      drawing itself is validated by compile plus the RF-027 hardware check
- [ ] Ties to the phase DoD: the transcript renders and a long reply does not overrun

## v0.5 scope notes

**Total effort:** roughly 12–17 days of work across five issues; one S, four M.
**Critical path:** RF-023 → RF-025 → RF-026 → RF-027 (with RF-024 joining at RF-026).
**Phase DoD (roadmap §v0.5):** `/chat-on` prints a prompt on serial and replaces the face with an empty
transcript; a line typed at `tools/board.py` appears on the screen as the outgoing message and its reply
appears there as it streams; a Ukrainian reply is legible on the panel — no boxes, no mojibake, no
half-characters at a line break; a reply longer than the screen scrolls or truncates deliberately rather
than overrunning the face area; `/chat-off` restores exactly the face and state that were showing
before; chrome behaves as it does outside the mode.
**Contracts pinned this phase:** **none — no seam changes.** The WS protocol, `EmotionFrame`, the
provider seams, `IFaceRenderer` and the capability flags are all untouched: the transcript is drawn into
the sprite `StubRenderer` already owns, and the console changes what is shown rather than what is sent.
The one new internal agreement — the column count shared by the wrap and the renderer — is pinned by
RF-024's test so the two halves cannot drift.
**Model note:** chat runs on **Gemini 2.5 Flash only** (`thinkingBudget: 0`) behind the `LLMProvider`
seam; **no paid APIs** — every provider seam is mocked and a fake device drives the protocol for unit +
integration tests. This phase adds no server-side code and no new provider call.
