## Finding 1 — 🔴 The face wipes the chrome, ~18 times a second

**`firmware/src/app/procedural_renderer.cpp`** — `compose()` began with `fillSprite(kBackground)`.

**Failure scenario.** The chrome and the face share one sprite by design, so they are pushed
together and cannot tear relative to each other. But they are drawn on *different schedules*:
`render()` runs when something happens — a state change, a link event — while `tick()` now runs
every loop and composes at ~18 FPS.

A full-sprite clear therefore erases the link indicator, the battery and the muted-microphone glyph
within 55 ms of every event, and they stay gone until the next event redraws them. On an idle
device that is essentially always.

The mute indicator is the one that matters most: DEVICE_UI keeps it permanently visible precisely
because a person is most likely to have muted the microphone by accident, and the only other way to
discover it is to speak and get no answer.

**Why the stub did not have this bug.** It redrew only on an event, so clearing everything cost
nothing — its own docstring even says the face "never draws into" the bands, which was true by
accident rather than by construction. A renderer that animates makes the difference visible.

**Proposed fix.** Clear and draw the face area only — `kFaceLeft, kFaceTop, kFaceWidth,
kFaceHeight` — leaving the bands to chrome, as DEVICE_UI §Layout says.

> Worth noting how this would have presented: as the chrome flickering. Nobody would have looked in
> the face renderer for it.

## Finding 2 — 🟠 "A settled face costs nothing" is not true

**`firmware/src/app/procedural_renderer.cpp`** — the early return in `tick()`.

The skip is guarded by, among other things, `idle.bob_y != 0.0f || idle.gaze_x != 0.0f`. The breath
is a continuous triangle wave: it is zero only at two exact instants per four-second cycle. So the
guard is true essentially always, the early return almost never fires, and the comment claiming a
settled face is free describes something that does not happen.

**Failure scenario.** Not a crash — a false belief. Someone reading that comment while chasing a
frame-budget problem would rule out the renderer as already-optimised and look elsewhere, which in
this project has repeatedly been the expensive path.

**Proposed fix.** State what actually happens. The skip is real but narrow: it catches the case
where the idle is *stilled* (`intensity` 0, which v2.2 uses during a turn) and nothing else is
moving. That is worth having and worth describing accurately.

## Finding 3 — 🟡 `areDistinct` is the wrong test for "did anything move"

`tick()` uses `areDistinct(frame, last_drawn_)` as part of the moved-since-last-frame check. But
`areDistinct` exists to answer a different question — *is this change worth animating* — and its
threshold (0.25) is coarse for that reason. Two consecutive frames of a slow crossfade are never
0.25 apart, so this term contributes nothing; the redraw happens because `isFading()` is true.

Harmless today because the other terms cover it. It becomes wrong the moment something changes the
recipe slowly *without* going through the crossfade — which is exactly what v2.2's emotion channel
with a long `ttl_ms` will do.

**Defer → v2.2**, where the emotion channel lands and this term will actually be load-bearing. A
per-field epsilon is the right answer and belongs with the code that needs it.

## Finding 4 — 🟡 The gaze drift moves the head, not the eyes

`tick()` applies `idle.gaze_x` to `geometry.centre_x`, which shifts every feature — so the face
"looks around" by moving its whole head a few pixels.

At four pixels this reads perfectly well and nobody would call it wrong. But the roadmap calls it
*gaze* micro-drift, and v2.4's proximity work plus v2.5's dual-mic direction both want a gaze that
moves the pupils independently of the head. Building that means the eyes gaining a pupil to move.

**Defer → v2.4**, which is the version that introduces the concept properly. Recorded here so it is
a known simplification rather than a thing someone later discovers and assumes was an oversight.

## What's solid

- **The pure/glue split held under a rendering workload.** Every decision — which recipe this frame
  is, what shape that means, how it is breathing — is in `src/pure/` and host-tested; the renderer
  owns buffers and the panel and nothing else. 27 new tests run in seconds with no board attached.
- **The seam was not touched.** v0.4 fixed `IFaceRenderer` against a stub specifically so v2 would
  implement rather than invent, and that is what happened. It is rare for a design decision made
  four versions early to still be exactly right.
- **A closed eye is drawn as a line.** `fillRoundRect` with zero height draws nothing, so the
  obvious implementation makes a blink into a disappearance. Catching that before hardware is the
  kind of thing the layer bank exists for.
- **The interrupted-crossfade case is handled and tested.** Two state changes inside a second is
  the common case in practice and the one nobody demonstrates.
- **Both frame rates are reported together.** After v1, where a display starved the microphone
  three times, this is the single most useful line in the status output.

## Fixes applied

### Fix 1 — the face clears only its own area (finding #1)

`compose()` clears `kFaceLeft, kFaceTop, kFaceWidth, kFaceHeight` instead of the whole sprite. The
chrome bands are left alone, as DEVICE_UI §Layout has always said they should be.

**Regression test.** None added, and the reason is worth stating rather than glossing: what broke
was the *interaction of two draw schedules on one buffer*, and the host cannot instantiate an
`M5Canvas`. A test asserting the clear rectangle's coordinates would restate the fix rather than
check it. This is a manual test instead — test 4 in `v2.1-manual-tests.md`, where the failure is
extremely visible.

**Verification.** `pio run -e cores3` compiles; flashed; `fps=16` steady; chrome present alongside
the animating face.

### Fix 2 — the comment describes what the code does (finding #2)

The early return is documented as what it is: a skip for a *stilled* idle rather than for a settled
face. Nothing about the behaviour changed.

**Architecture impact.** None to any contract. One convention worth carrying into v2.2: **the face
and the chrome share a buffer but not a schedule.** Anything that draws into the sprite on its own
cadence must confine itself to its own region, or it will erase whatever else was there. This is now
true of the renderer and will be true of v2.3's lip-sync overlay.
