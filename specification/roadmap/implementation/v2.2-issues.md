# v2.2 — GitHub Issues

Issues for phase **v2.2 — The emotion channel** (version **v2 — Living face**), derived from the
per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§v2.2) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§Contracts, §EmotionFrame, §Turn lifecycle, §The face,
§Seams, §Testing). This file is scoped to a single phase; IDs continue from the previous phase
(RF-058 → **RF-059…RF-063**).

This phase moves the last decision off the device. Until now the face has been driven by
`recipeFor(DeviceState)` — the firmware looked at its own state machine and chose an expression.
v2.2 makes the **server** decide: Gemini reports its own emotional state alongside the reply, the
server validates it against the fixed enum and turns it into an `EmotionFrame`, and the device
renders what it is given. It touches three of the five pinned seams at once — the WS protocol
(`emotion{}`), the `LLMProvider` seam (a reply is no longer only text), and `IFaceRenderer`
(`show(DeviceState)` → `show(const EmotionFrame&)`) — which is why the phase is decomposed around
the seams rather than around the components.

**Reconciled against the real implementation** (`generate-issues` Step 0.5). Three divergences
between `ARCHITECTURE.md` and the code as built, all resolved in favour of the code and closed by
this phase:

| | The document says | The code does | Closed by |
|---|---|---|---|
| `IFaceRenderer::show` | `show(const EmotionFrame&)` (§The face) | `show(roboface::DeviceState)` | RF-063 |
| `emotion{}` | listed in the server→device message set (§Contracts) | `ServerMessage::kEmotion` is declared and explicitly **not handled** (`firmware/src/pure/ws_protocol.h:373`) | RF-063 |
| `LLMProvider.stream` | not specified beyond "one seam per service" | yields bare `str` deltas — no room for a reported emotion | RF-061 |

Two further facts from v2.1 that this phase must not undo:

- **The turn ends when the device has finished speaking, not when the server has finished sending**
  (`v2.1.2`). The device buffers seconds of voice the server has already sent. Any `speaking` flag
  arriving from the server is therefore a *permission*, never the thing that decides when the mouth
  stops — see RF-063.
- **The face and the chrome share a buffer but not a schedule** (v2.1 code review, "Architecture
  impact"). Anything drawing into the sprite on its own cadence confines itself to its own region.

## v2.2 — The emotion channel

### RF-059 — The `EmotionFrame` contract and the emotion enum

**Description:**
The object the whole phase exchanges, in `server/roboface_server/protocol.py`: the fixed emotion
enum, the frame, and the validation that makes an untrusted model report safe to render. Nothing
sends it yet — this issue is the shape and the guarantees, so the other four agree on both.

**What needs to be done:**
- `Emotion(StrEnum)` — exactly `neutral · calm · joy · thinking · surprised · sad · error`
  (ARCHITECTURE §EmotionFrame). No eighth value: the device's recipe table must be total over it,
  and a value the firmware cannot render is a blank face rather than an error.
- `Gaze` and `EmotionFrame` as frozen slotted dataclasses matching the documented JSON exactly:
  `emotion` and `intensity` required; `gaze`, `accent_color`, `speaking`, `ttl_ms` optional with the
  documented defaults (centre, none, `false`, `8000`).
- **A `from_model()` classmethod that never trusts its input** — this is the issue's real content.
  An unknown or misspelled emotion becomes `neutral`; a missing one becomes `neutral`; intensity is
  clamped to 0..1 and a non-numeric one becomes a documented default; gaze components clamp to
  −1..1; a malformed `accent_color` is dropped rather than passed through. Every coercion is
  silent to the wire and **logged once** at debug — a model that keeps reporting `"happy"` is a
  prompt bug, and it must be findable.
- Encoding through the existing text codec: `emotion{}` is a JSON frame, so it goes through the
  same envelope path as `reply` and needs no new transport.
- Omit optional fields that are at their default rather than sending them: the device applies the
  same defaults, and a frame is sent on every state change.

**Dependencies:** None

**Expected result:**
`EmotionFrame` exists, round-trips through the codec, and cannot be constructed from model output
in a state the device would refuse to render.

**Acceptance criteria:**
- [ ] The enum is exactly the seven documented values, and `from_model` is total over arbitrary input
- [ ] **Contract test:** `tests/contract/test_emotion_frame.py` pins the JSON shape, the field names,
      the enum membership and every default — the file that must change when the contract does
- [ ] **Unit test:** the coercions, one case per rule (unknown emotion, absent emotion, out-of-range
      intensity, non-numeric intensity, out-of-range gaze, malformed colour), **LLM mocked by default**
- [ ] `ARCHITECTURE.md` §EmotionFrame matches the implementation field for field, corrected in this
      commit if it does not
- [ ] Ties to the phase DoD: "a malformed or unknown model emotion never reaches the screen"

### RF-060 — The emotion engine: turn state + model report → frame

**Description:**
`server/roboface_server/emotion.py` — the mapping that decides what the face does, kept as pure
functions with no I/O so it is testable without a turn. This is the module ARCHITECTURE §2 names as
"an emotion engine (decides `EmotionFrame` from the turn and the model's own reported state)".

**What needs to be done:**
- `frame_for(state, report=None, speaking=False)` → `EmotionFrame`. The documented mapping:
  `listening` → `calm`, `thinking` → `thinking`, `replying` → **the model's reported emotion**
  (falling back to `neutral` when there is no report), an enumerated failure → `error`, and idle →
  `neutral`. Total over the turn states, so a state added later fails at the type level rather than
  on the screen.
- An accent colour per emotion — one table, hex strings. This is the value v2.6's skins and v5's
  halo read; deciding it here rather than per-skin is what makes "a skin is an asset swap" true.
- `ttl_ms` per state, not one constant: a `thinking` frame should outlive a slow model call, while
  an idle `neutral` needs no expiry pressure at all. State the reasoning next to the numbers.
- `speaking` set from whether the turn is currently producing TTS — and documented at the call site
  as a **permission for the device's lip-sync, not a duration**: the device is seconds behind the
  server's idea of when speech ends (see the phase preamble).
- Gaze stays centre in this phase. v2.5 (direction) and v3 (the vision turn) are its real sources;
  inventing a gaze here would be a later phase's scope arriving early.

**Dependencies:** RF-059

**Expected result:**
Given a turn state and an optional model report, the server produces exactly one `EmotionFrame`,
by a rule that is readable in one screen and total over the enum.

**Acceptance criteria:**
- [ ] `frame_for` is total over the turn states and over the emotion enum
- [ ] **Unit test:** every state maps to its documented frame; a `replying` state with no report
      yields `neutral`, not a crash; the accent table has an entry per emotion; **LLM mocked**
- [ ] The mapping table and the `ttl_ms` choices carry their reasoning in comments
- [ ] Ties to the phase DoD: "the face's expression comes from the server for every turn and state change"

### RF-061 — Structured output from Gemini: `{emotion, intensity, reply}`

**Description:**
The model reports its own state alongside the reply. This changes the `LLMProvider` seam — a reply
is no longer only text — and it must do so **without costing time-to-first-delta**, which is the
number the whole architecture exists to keep small. Touches `providers/base.py`,
`providers/gemini.py`, `providers/mock.py` and the orchestrator's consumption of the stream.

**What needs to be done:**
- **The seam.** `LLMProvider.stream()` yields a small tagged union instead of `str`: a reply-text
  delta, or the model's emotion report. A union rather than a second method because the two arrive
  interleaved on one connection, and a second call would be a second turn's worth of latency.
- **The schema order is the design.** Gemini's `response_schema` puts `emotion` and `intensity`
  **before** `reply`, so the report arrives in the first chunk and the face can change *before* the
  first word is spoken. A schema with `reply` first would stream the whole answer before the server
  learned how it felt, which is the same latency mistake as a second call, spelled differently.
- **An incremental JSON reader as pure logic** — its own module with its own unit tests, fed one
  network chunk at a time. It must emit the scalar fields as soon as they complete and stream the
  `reply` string's *contents* as deltas, handling: a chunk boundary inside a token, inside a string,
  inside an escape sequence, and inside a multi-byte UTF-8 character. Ukrainian text is two bytes a
  letter, so the last of those is the default case, not the edge case.
- **The mock provider gains the same shape**, including a way for a test to script the reported
  emotion. No paid API in any test.
- Keep `thinkingBudget: 0` and Gemini as the only chat implementation (CLAUDE.md).
- The system prompt gains the instruction to report an emotion from the enum — and the validation in
  RF-059 stays the authority, because a prompt is a request, not a guarantee.

**Dependencies:** RF-059

**Expected result:**
A turn yields the model's emotion in its first chunk and its reply text as deltas, with
time-to-first-delta unchanged.

**Acceptance criteria:**
- [ ] **Contract test:** the `LLMProvider` seam's new yield type, pinned for both the real provider
      and the mock — the provider-seam contract test updated in this same commit
- [ ] **Unit test:** the incremental reader against chunk boundaries in every position named above,
      including inside a multi-byte character; the reply text reassembles byte-identically
- [ ] **Unit test:** a model that reports an emotion outside the enum, or no emotion at all, still
      produces a complete reply — the turn never fails on the report
- [ ] `ARCHITECTURE.md` §Seams updated for the changed provider seam, in this commit
- [ ] Time-to-first-delta measured in the integration test is not worse than the text-only path
- [ ] **LLM mocked by default**; the live call stays opt-in behind `ROBOFACE_LIVE_TESTS=1`

### RF-062 — The server emits `emotion{}` per turn and on state change

**Description:**
Joins RF-060 and RF-061 to the wire: the orchestrator yields an emotion event, and the router sends
`emotion{}` — per turn **and on every state change, including outside a turn**, which is the part
that is easy to half-implement. Touches `orchestrator.py` and `router.py`.

**What needs to be done:**
- A new `TurnEvent` variant carrying an `EmotionFrame`, yielded by the orchestrator: once when
  listening opens, once when the model call starts, and once when the reported emotion arrives —
  **before** the first reply delta, so the face changes as the device starts to speak rather than
  after.
- The router sends frames for the transitions the orchestrator cannot see: a connection going idle
  after `tts_end`, an enumerated `error{code}` (which pairs with the `error` emotion), and the
  return to `neutral` when a turn is abandoned or cancelled mid-stream.
- **Cancellation.** A turn cancelled mid-stream must still leave the face somewhere deliberate. The
  §10 `finally` path is where that belongs; a cancelled turn that leaves the last emotion standing
  is a face stuck in `thinking` until the ttl expires.
- No emotion frame for a state the device already knows locally — `boot`, `wifi_connecting`,
  `offline` are device facts, not server opinions, and sending them would create two authorities for
  one screen.

**Dependencies:** RF-060, RF-061

**Expected result:**
Driving a full turn against the fake device produces the documented frame sequence, and no path
through the router leaves the face on a stale expression.

**Acceptance criteria:**
- [ ] **Integration test:** a full turn against the fake device asserts the exact `emotion{}`
      sequence and its ordering relative to `reply` and `tts_audio`
- [ ] **Integration test:** a turn cancelled mid-stream, and one aborted by a provider error, each
      leave a deliberate final frame
- [ ] **Contract test:** the `emotion{}` frame's place in the turn lifecycle, added to
      `tests/contract/test_turn_lifecycle.py`
- [ ] The emotion frame precedes the first reply delta for the same turn
- [ ] Ties to the phase DoD: "for every turn and state change"

### RF-063 — The device renders the frame it is given

**Description:**
The firmware stops choosing expressions. `emotion{}` is parsed in pure logic, the recipe table is
re-keyed from `DeviceState` to `Emotion`, `IFaceRenderer::show` takes an `EmotionFrame`, and `ttl_ms`
relaxes the face to `neutral` when frames stop arriving. Touches `firmware/src/pure/` (parser,
recipe table, ttl) and `firmware/src/app/` (the renderer and `main.cpp`).

**What needs to be done:**
- **Pure:** an `EmotionFrame` struct and its parser in `ws_protocol.h`, replacing the explicit
  "this phase does not handle `emotion`" case at `ws_protocol.h:373`. Missing optional fields take
  the documented defaults; an unknown emotion string becomes `neutral` — the device applies the same
  rule as the server rather than trusting that the server already did, because the two are separately
  releasable.
- **Pure:** `recipeFor(Emotion)` replacing `recipeFor(DeviceState)`, total over the seven emotions,
  with `intensity` scaling expressiveness (smile depth, eye opening, idle amplitude) rather than
  selecting a different recipe.
- **Pure:** ttl relaxation — with no frame for `ttl_ms`, the face crossfades back to `neutral`. It
  composes with the existing `Crossfade`, which already relaxes over `kRelaxMs`.
- **The seam:** `IFaceRenderer::show(const EmotionFrame&)`, bringing the interface to what
  ARCHITECTURE §The face has always documented. Its contract test and the ARCHITECTURE line change
  in this same commit.
- **The device's own states stay local.** `boot`, `wifi_connecting`, `offline` and a local fault are
  facts the server cannot know; they keep a local frame. With the socket down the device relaxes to
  `neutral` and keeps its idle loop — the DoD says so explicitly.
- **`speaking` is a permission, not a duration.** It may gate the lip-sync, but what decides when the
  mouth stops is the device's own `audio.isSpeaking()`. `v2.1.2` fixed exactly this: the server's
  idea of when speech ends is seconds ahead of the speaker, and taking it literally froze the mouth
  mid-reply. A regression here would look like a hardware fault.
- **Closes v2.1 review finding #3** (`areDistinct` was the wrong threshold for "did anything move").
  It was superseded during v2.1 by `changedVisibly`; confirm and mark it resolved in
  `v2.1-code-review.md` rather than leaving a deferred finding pointing at code that no longer
  exists.

**Dependencies:** RF-059

**Expected result:**
The face on the screen is the frame the server sent; with the server gone it relaxes to `neutral`
and keeps breathing.

**Acceptance criteria:**
- [ ] **Contract test:** `IFaceRenderer`'s signature and the parsed `EmotionFrame` field set, with
      `ARCHITECTURE.md` §The face corrected in the same commit
- [ ] **Host test** (`pio test -e native`): the parser over well-formed, partial and malformed
      frames; `recipeFor` total over the emotion enum; intensity scaling; ttl relaxation under an
      injected clock
- [ ] **Host test:** `speaking=false` arriving while the speaker is still draining does **not** stop
      the mouth — the regression test for the `v2.1.2` fix
- [ ] `pio run -e cores3` compiles; no `M5` include reaches `src/pure/`
- [ ] Manual DoD check on hardware: the expression follows the server; pulling the server relaxes the
      face to `neutral` with the idle loop still running
- [ ] Ties to the phase DoD: "with the server unreachable the device relaxes to `neutral` and keeps
      its idle loop"

## v2.2 scope notes

**Total effort:** roughly 19 points (M+M+L+M+L) — about three to four weeks of one person's work,
and the phase's largest single risk is RF-061's incremental reader.

**Critical path:** RF-059 → RF-061 → RF-062. RF-063 is the same length but starts at the gate, so
the firmware is not on the critical path unless RF-061 finishes early.

**Phase DoD (roadmap §v2.2):** the face's expression comes from the server for every turn and state
change; a malformed or unknown model emotion never reaches the screen; with the server unreachable
the device relaxes to `neutral` and keeps its idle loop.

**Contracts pinned this phase:** the **WS protocol** (`emotion{}` — RF-059, RF-062), the
**`EmotionFrame`** face contract (RF-059, RF-063), the **`LLMProvider` provider seam** (RF-061) and
**`IFaceRenderer`** (RF-063). Four of the five seams move in one phase, which is why each carries
its `ARCHITECTURE.md` update and its contract test in the same commit rather than at the end.

**Model note:** chat runs on **Gemini 2.5 Flash only** (`thinkingBudget: 0`) behind the
`LLMProvider` seam; **no paid APIs** — every provider seam is mocked and a fake device drives the
protocol for unit + integration tests.
