## Detailed Results

### RF-048: The VAD endpointer, as pure logic
**Status:** completed · **Commit:** `8ae583b`
**Validation:** [x] pio native 196 · [x] cores3 compiles · [x] acceptance

`roboface::Endpointer`, fed one frame at a time, reporting transitions rather than levels.
**Two measures, not one:** energy alone calls a slammed door speech, and it calls *rumble* speech —
the captures that cost v1.3 an evening measured a healthy level and carried no voice at all. Voiced
speech crosses zero far more often than a sub-100 Hz thump, which separates them for one comparison
per sample. Sub-minimum speech is `kDiscarded`, never a start/end pair.

### RF-049: Active listening — pre-roll, and a window opened without a finger
**Status:** completed · **Commit:** `81a40aa`
**Validation:** [x] pio native 205 · [x] cores3 compiles · [x] acceptance

`startMonitoring` captures with no uplink so the endpointer hears the room before anything asks for
a window. On speech the pre-roll ring is flushed ahead of live audio — detection takes a few frames
to be sure and those frames are already words. A refused `listen_start` resets the endpointer,
honouring v1.2's rule that the server owns the window.

**Correction recorded during execution.** The issues file's reconciliation note claimed capture was
already always-on from v1.3. That was true of a change reverted earlier the same night; on the code
as it stands `startListening` begins the microphone and `stopListening` ends it. v1.4 therefore
introduces continuous monitoring itself. *The note was written from a memory of the code rather than
from the code.*

### RF-050: Half-duplex — the device must not answer itself
**Status:** completed · **Commit:** `046bb0d`
**Validation:** [x] pio native 214 · [x] cores3 compiles · [x] acceptance

Playback suspends the monitor; **every** route out of playback resumes it, which is why resumption
lives in `releaseBus` and nowhere else. The failure that matters is not listening that resumes late
but listening that never resumes: a reply ended by an unanticipated path leaves the device
permanently deaf while looking perfectly healthy — connected, idle, a face on the screen.

### RF-051: Sensitivity, end-pause, and the switch back to PTT
**Status:** completed · **Commit:** `8cfc1d2`
**Validation:** [x] pio native 218 · [x] cores3 compiles · [x] acceptance

`/vad on|off|sens|pause` changes the values without a reflash — a reboot changes the room, the
distance and the speaker along with it, which makes a reflash-per-comparison worthless. Out-of-range
values are **refused, not clamped**. The keys default in `main.cpp` as well as the example, because
`config.h` is gitignored and a new key must not turn someone's next pull into a compile error.

### RF-052: The recogniser's endpointing closes the utterance
**Status:** completed · **Commit:** `e294d77`
**Validation:** [x] pytest 496 · [x] ruff · [x] strict mypy · [x] acceptance

**Architecture impact — the turn lifecycle changed, and `ARCHITECTURE.md` changed with it in the
same commit.** The recogniser now ends the utterance and the device's end-pause is the backstop.
Two consequences are pinned by `tests/contract/test_turn_lifecycle.py`: a `listen_stop` for an
already-settled utterance is idempotent rather than an error, and binary frames arriving after the
settle are dropped quietly. Calling either one a protocol violation would put a fault on the screen
for every hands-free turn.

**A stated limit:** the settle is noticed on the *next* audio frame — at most one frame (20 ms)
late. An utterance settling on its final frame is closed by `listen_stop` through v1.3's path.

**The mock had to become honest first.** `MockASRSession` replayed its script the moment anyone
iterated it, modelling a recogniser that decides before hearing anything. Under v1.3 that was
invisible because nothing read the result until `finish()`; v1.4 reads it *during* the window, so
every utterance ended on its first frame. `settle_after` now models endpointing. **A mock that is
wrong in a way the current code cannot notice is a trap set for the next version** — this one had
been waiting since v1.3.

## Next Steps

No board testing was run during implementation, by request: all six issues are to be tested
together now that the phase is implemented. Everything above is proven in software — the DoD is
proven on the Core S3 only once that run happens, and the table says so plainly rather than
implying hardware confirmation the phase has not had.

Two things to carry in, both from the same night's debugging:

1. **The capture level threshold is narrow.** Recognition tracked RMS closely: −10 dBFS
   transcribed 146 characters, −25 dBFS returned nothing. The VAD's `sensitivity` is a *peak*
   threshold on the device and is a different question from whether the recogniser can hear what is
   sent — tuning one does not tune the other.
2. **PSRAM reports `found=1 size=0`**, leaving ~53 KB of internal RAM. RF-049 added a ~9.6 KB
   pre-roll ring to that budget, and RF-050's guard exercises the mic/speaker switch where
   `i2s_alloc_dma_buffer` was already seen to fail. Homed to the v1 HARDEN sweep, and it should be
   taken seriously there rather than deferred again.
