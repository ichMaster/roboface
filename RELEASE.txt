Version 1.3.0 (2026-08-28)
---------------------------
Roadmap phase v1.3 -- ASR and the full voice loop. **Speak, and be answered by
voice.** All three stages now stream and the loop closes.

- The ASRProvider seam is a **session**, not a call: audio is pushed in while
  transcripts are read out. A transcribe(audio) -> str shape could only begin
  once the audio was complete, which costs about 1.4 s at the worst possible
  moment -- after the person stops talking and starts waiting. Encoding that in
  the seam means no implementation can quietly reintroduce it.
- Deepgram over wss://, with interim_results, smart_format, server-side
  endpointing (~500 ms) and an utterance_end_ms (~1000 ms) backstop. The URL
  builder is its own tested function because none of those parameters fail
  loudly when wrong: omit interim_results and there are simply no interims,
  which looks like a slow network. One test asserts the backstop is longer than
  the endpoint -- a relationship invisible in either number alone.
- **The phrase-hold.** Deepgram's speech_final means "this span is settled", not
  "the speaker stopped"; a breath mid-sentence produces one, usually without
  terminal punctuation. It is held for the continuation or the backstop.
  Answering it immediately is the character talking over someone mid-sentence,
  which reads as rudeness rather than as a defect, and no amount of speed makes
  up for it.
- Interims replace rather than accumulate. Deepgram revises constantly -- "прив"
  becomes "привіт" becomes "привіт як" -- and accumulating puts every draft on
  the screen at once.
- Per-stage budgets: ASR <= ~5 s on *resolution* after the audio stops, LLM
  first token <= ~8 s, TTS first audio <= ~3 s, each on that stage's first
  output. A breach maps to that stage's own error code, so a log says which leg
  failed.
- Three latency numbers logged separately -- asr.resolved, turn.first_delta_ms,
  and turn.speaking's ms_since_listen_stop. The DoD is a claim about which leg is
  smallest, and one combined figure could neither support nor refute it.
- The device renders asr_partial and asr on serial only. A transcript is the last
  thing that belongs on the screen: a device state is a face or an indicator, and
  a *guess* about what you just said is not even a state.

Review fix: asr_partial was computed, queued and never sent. The frame existed
and the firmware rendered it; the line that forwards them was never written. A
feature can be complete at both ends and absent in the middle, and neither end's
tests notice.

Recognition is optional exactly as speech is: without a DEEPGRAM_API_KEY the
device still types.

Version 1.2.0 (2026-08-27)
---------------------------
Roadmap phase v1.2 -- microphone capture and push-to-talk. **The device can send
what it hears, while you are still saying it.**

Measured on hardware, with per-frame timestamps: listen_start at +0.00 s, first
audio at +0.07 s, last at +3.06 s, listen_stop at +3.07 s -- 151 frames spread
evenly across the window. The first frame arrived 3.01 s before the stop, and
the spread is the part that matters: a burst just before the stop is what a
device that buffered the utterance produces, and it is what v1.3's recognition
cannot work with.

- The listening window is a pinned contract. listen_start opens
  BinaryPhase.LISTENING, binary frames mean `audio` only inside it, listen_stop
  closes it. All three names were declared in v0.1 and device_binary_meaning
  already returned AUDIO; what was missing was the typed frames and the router
  state -- exactly as v0.1's own comment on _handle_binary predicted.
- The utterance is capped in **bytes rather than seconds**: bytes are a property
  of what arrived, seconds would have to be trusted across a network. Checked
  before storing, so the memory the cap protects is never taken, and exceeding it
  ends the window with an enumerated error rather than truncating.
- listen.stop logs a digest of the assembled audio, because a byte count is
  satisfied by reordering and by duplication and a digest is not.
- Press-and-hold on the glass, with the rules in pure/ptt.h driven by an injected
  clock: proving "a 100 ms tap is not an utterance" on hardware means tapping the
  glass for exactly 100 ms.
- The input-level meter fills the bottom-band tenant v0.4 declared and nothing
  had yet contended for. No text is drawn -- the bar is the message.
- /loopback records and replays locally, sending nothing to the server, and
  reports the peak level it captured.

Four faults found by measuring on the device, three with symptoms pointing away
from their cause:

- A 3 s window captured 2.26 s. One microphone buffer was armed at a time, so
  the mic idled between frames; it has a two-deep queue like the speaker, and
  keeping both armed gives 2.86 s.
- The first hold worked and every later one was refused: listen_stop leaves the
  device *thinking*, which is right from v1.3 where recognition follows. v1.2 has
  neither, so it thought forever.
- Capture read 1% of full scale. M5Unified's default mic magnification of 16 is
  far too low for this board's ES7210; at 64, speech reads 30-70%. This one had
  the longest reach -- streaming would have "worked" until v1.3 and failed there
  as poor recognition, which looks like a model problem and is a gain setting.
- Loopback playback was silent while TTS played fine. playRaw returns true even
  when both channel slots are full, so draining an already-buffered recording
  handed it everything at once and recycled the pool buffers underneath audio the
  I2S task had not read.

Review fixes: the server releases an in-flight utterance when a socket drops
(the cap bounds a live utterance, not how many dead ones accumulate), and the
device stops capturing when the server refuses a window rather than earning a
bad_frame per frame for as long as a finger is down.

Version 1.1.0 (2026-08-25)
---------------------------
Roadmap phase v1.1 -- streaming TTS playback. **A typed line is answered out
loud, and the mouth opens before the sentence exists.**

Measured on hardware: speech began 3.3 s before the model finished writing on a
short reply, and 14.8 s before on a long one.

- sentence.py -- the PhraseSplitter. A phrase closes at a sentence or clause
  boundary **only when the boundary is followed by whitespace**, and the
  whitespace is the whole point: it turns "is this a sentence end?" from a guess
  into an observation, and makes "not yet" an answer distinct from "no". Without
  that distinction "3.5" becomes two spoken phrases, in two synthesis calls, with
  a pause between them. Eighteen Ukrainian abbreviations are matched at a word
  boundary so "ст." does not fire inside "віст.".
- The TTSProvider seam, and ElevenLabs behind it. Speech is not chat, so this is
  a second vendor seam rather than a breach of the Gemini-only rule. pcm_16000 is
  exactly the device's playback format, so nothing decodes on the server or on
  the board.
- Transport widened to carry bytes. The message types tts_audio, tts_end and
  tts_failed had existed since v0.1, and server_binary_meaning already gave an
  unlabelled binary frame its meaning -- but Transport.send() took only str, so
  there was no way to put audio on the wire at all. That gap, not the vocabulary,
  is what this phase opened. A turn now emits ReplyDelta | AudioChunk, because
  the two interleave and a merge done by the consumer is where the interleaving
  would be lost.
- The orchestrator speaks while it writes: each delta is yielded first, then fed
  to the splitter, so text never waits behind audio. The first-audio budget sits
  on each phrase's first chunk -- a stalled vendor fails fast, a slow-but-flowing
  one is never cut off mid-phrase.
- Firmware audio_io: PCM arriving over the socket comes out of the speaker as it
  arrives. The shared I2S bus is claimed once per turn and given back on tts_end.

Four device faults were found on hardware, none reachable from a host test, and
each sounded like a different problem than it was:

- Silence while the server logged hundreds of chunks sent -- PSRAM reports zero
  free on this board, so the backlog never allocated, and write() discarded every
  chunk while telling the caller it had accepted them. It now falls back to
  internal RAM, reports what it got, and counts what it drops.
- "The beginning is good and then the sound breaks up" -- M5.Speaker.playRaw does
  not wait for a free slot: it returns false and drops the chunk. The network
  outruns 16 kHz within a second, so everything after that was discarded. The
  backlog is now fed only as fast as playRaw accepts, and a refused chunk goes
  back to the *front* of the ring, because appending it would reorder the reply.
- Distortion -- playRaw keeps the pointer rather than copying, and was handed a
  stack buffer; channel -1 also let consecutive chunks sound together rather than
  queue.
- The speaker held the I2S bus for the rest of the session -- ws.cpp whitelists
  which parse results become a frame event, and tts_end was not on the list, so
  it was discarded one layer below main.cpp.

Review fixes: a failed phrase now closes its TTS stream (it leaked an open HTTP
response per failure, the same defect v0.2 closed for the LLM stream), and the
device no longer reports success for audio it discarded.

Known, deferred: PSRAM reports zero free despite qio_opi and BOARD_HAS_PSRAM.
Audio runs on a 48 KB internal fallback. **v2's renderer and v3's JPEG buffers
assume PSRAM exists**, so this is carried to v3.1 and is a candidate for the
end-of-phase hardening sweep.

Version 0.5.1 (2026-08-24)
---------------------------
The end-of-phase hardening sweep for v0. One deferred MEDIUM finding, fixed.

- The transcript's wrap is cached instead of rebuilt on every repaint. It used to
  wrap the whole accumulated reply and discard all but the last nine lines, per
  frame: at 26 columns and a 2048-byte buffer that is up to ~80 std::string
  allocations, and while a reply streams the repaints run at the 33 ms cap, so
  roughly 2400 short-lived allocations a second on a heap that is not compacted.
  The wrap is pure and its inputs change only on append, so it is now computed
  once per change.

  A cache's failure mode is staleness, so five host tests assert the invalidation
  and each reads *before* the mutation -- the order the repaint loop uses. They
  were checked against the bug they exist for: removing the invalidation from
  appendReply fails two of them. Verified on hardware as well, with a streaming
  Ukrainian reply growing on the panel as it arrived.

This closes every HIGH and MEDIUM finding raised across phase v0 -- v0.1 through
v0.5. The two remaining LOW findings stay deferred to their documented homes.

Version 0.5.0 (2026-08-24)
---------------------------
Roadmap phase v0.5 -- the serial chat console. The face shows a turn's state;
now the board can show its content, in Ukrainian, on the panel.

- /chat-on turns the board into a chat console: what you type and the reply as it
  streams are drawn where the face usually is. /chat-off gives the screen back.
  It borrows the screen the way the /faces self-test does -- explicitly entered,
  explicitly left -- and does not relax the rule it sits next to: MISSION forbids
  showing a *state* as a word, and a transcript is content, not a state label.
- Ukrainian renders on the panel. M5GFX bundles no Cyrillic face -- its efont set
  is JA/CN/KR/TW and Font0 is ASCII -- but it accepts U8g2 font arrays through
  lgfx::U8g2font, the same mechanism its own fonts use, and decodes UTF-8 when
  drawing. So this is an embedded array rather than a text pipeline: -Misc-Fixed
  10x20, public domain, 387 glyphs. Coverage was verified by decoding the array's
  own glyph table rather than trusting its name -- the Ukrainian letters Russian
  does not use are the ones a "Cyrillic" font quietly omits, and the omission only
  shows on the first word that needs one.
- pure/transcript.h wraps by codepoint, not by byte. Ukrainian is two bytes per
  letter, so a byte-based wrap would fit half as many letters per line as it
  thought and would cut characters in half at the break -- which draws as a box,
  not as a bad line break. A reply frame can also end mid-character, because the
  server streams bytes; an incomplete trailing sequence is held back until the
  frame that finishes it. The test that matters splits a reply at every byte
  offset and asserts the lines match appending it whole.
- The console grid lives in pure/layout.h and is read by both the wrap and the
  renderer, so they cannot drift. A host test pins it -- and caught the claim,
  written in two comments, that 264/10 and 184/20 divide exactly. They do not.
- Repaints keep v0.4's discipline: a delta marks the sprite dirty and the 33 ms
  cap decides when to paint. The loop's push path had to learn to redraw the
  console as well as chrome; without that a dirty transcript would never have
  reached the panel.

Review fixes, all in the glue layer the pure/glue split predicts defects in:

- /chat-off no longer reverts the device state. It saved the state on entry and
  put it back on exit, by analogy with the self-test -- but the self-test *drives*
  state and the console does not. Lose the link while the console is open and the
  old behaviour put the idle face back on a device with no socket. It now renders
  whatever state the device is genuinely in.
- Each drawer sets its own font. Nothing in the firmware set one, so once the
  console had drawn its 20 px Cyrillic face into the sprite, chrome's fault code
  and the debug line rendered in it too -- and kept doing so after /chat-off.
- /chat-on refuses while the self-test is running. Two borrowers of one screen,
  each with its own idea of what to give back, made the self-test invisible.

Known gap: the font covers ASCII and U+0400..U+0523, so General Punctuation --
en dash, em dash, the typographic apostrophe -- draws as nothing. The first long
Ukrainian reply of the hardware check contained two of them. Words are
unaffected, which is why the DoD passes; it is recorded in the font source,
TESTING.md and DEPLOYMENT.md.

Version 0.4.1 (2026-08-24)
---------------------------
Post-release fixes on phase v0.4. The server moved off the development Mac, which
cannot host it, onto a Linux box on the same LAN. The board now reaches it and a
text turn completes end to end: typed at the board, answered by Gemini, rendered
as a state on the panel.

- The Mac cannot serve the board, and this is not a bug in the firmware. Its
  endpoint filtering accepts an inbound LAN connection and then destroys the
  socket before the application's first read (errno 57, ENOTCONN). It is a
  socket-layer filter, which is why it was so hard to see: the TCP handshake
  completes, so `nc -z` calls the port open and only the first read fails. Not the
  Application Firewall's per-app allowlist -- an explicitly allowed binary fails
  identically -- and not the router, which needs no changes at all.
- tools/remote.sh: deploy and administer the server on a remote box over plain
  SSH -- deploy, start, stop, restart, status, health, logs, ping, shell. No
  systemd and no sudo; start/stop is a PID file and a log file. `health` asks its
  two questions from the workstation, because a listener the board cannot reach is
  not a running service.
- DEPLOYMENT.md: the server's lifecycle, the same operations written out in plain
  ssh for a machine with no checkout, and the firmware's build/flash/config half.
- tools/board.py never read stdin, so every line typed at it was discarded; only
  --send worked. It is two-way now. Transient CDC read failures after a write are
  absorbed rather than treated as a disconnect -- reattaching threw away exactly
  the output that mattered, the reply to the command just sent. The drop message
  no longer claims the board reset, which the uptime counter disproves.
- server/.env is no longer sourced into the shell anywhere. It was redundant --
  load_settings() reads the file itself, by a path derived from config.py's own
  location -- and lossy: WEATHER_URL's value contains an unquoted `&`, so the
  shell backgrounds there and the assignment never arrives. Exit code 0, no
  message. As _resolve() reads the environment before the file, a mangled value
  would have overridden the correct one rather than merely going missing.
- chat.py and firmware/src/config.example.h point at the server box. The firmware
  needs a literal address: it links no mDNS resolver, so the .local name the
  host-side tools could use would never resolve there.
- TESTING.md 5 rewritten. It had described the link as an unresolved blocker and
  suggested a tunnel that cannot work -- the firmware speaks ws:// only -- and its
  account of the failure named the wrong mechanism.

Version 0.3.0 (2026-08-24)
---------------------------
Roadmap phase v0.3 -- Firmware skeleton: Core S3 as a WSS client. The first C++
in this repository, and the first code that runs on the hardware.

- firmware/: a PlatformIO project with two environments, and the split between
  them is the architecture. `native` compiles only src/pure/ -- header-only,
  Arduino-free -- so an #include <M5Unified.h> reaching pure code fails the host
  build. 64 host tests now run on a laptop with no board attached.
- pure/ws_protocol.h: the device half of the WS protocol seam, mirrored from the
  released protocol.py. Both vocabularies, all twelve error codes including
  bad_frame, proto_ver 1, pcm16/16000/1, the frame cap. A declared-but-unhandled
  type parses as unsupported rather than malformed, and an unrecognised error code
  still parses -- a device that cannot parse an error cannot report one.
- pure/state.h: the specified state machine, with a transition function that is
  total over (state, event). pure/backoff.h: exponential, capped, jittered.
  pure/line_reader.h: bounded, CRLF-aware. pure/ws_url.h: the SERVER_URL parser.
- app/net.cpp and app/ws.cpp: WiFi bring-up with a reconnect supervisor, and the
  WebSocket client. Glue owns the hardware and decides nothing; every schedule
  comes from the tested pure half.
- main.cpp: the serial debug channel. A typed line becomes a text_in and reply
  deltas print as they arrive, inside the receive path -- a buffered version would
  satisfy the wording and lose the property v0.2 exists to provide.
- tests/contract/test_firmware_mirror.py: reads the C++ header and compares it to
  protocol.py in the Python CI job, so a drift between the two languages is caught
  by someone who never runs pio.

The transport is ws://, not wss://. The server runs uvicorn with no TLS, so
ARCHITECTURE now records the gap rather than promising a transport the product
does not offer. Closing it is one line in config.h plus a certificate.

Four bugs were found by the tests and the hardware: a state machine that claimed
`idle` while unable to reach the server; two build environments compiling the same
headers under different C++ standards; a URL parser accepting port 0 and 70000;
and `Serial` writing to the UART pins instead of USB, which made the debug channel
-- this version's only turn source -- silent while the board ran perfectly.

Code review fixed three more: the first connection attempt was aborted and
restarted microseconds later, the reconnect log described a delay it never waited,
and the device had inherited the server's 64 KiB frame cap, which is a fifth of
this board's RAM.

Definition of Done: `pio test -e native` passes and `pio run -e cores3` compiles
clean. On hardware, the board joins WiFi, parses its server URL, holds
`wifi_connecting` correctly and backs off with jitter exactly as the host tests
predict. The end-to-end turn is NOT yet verified: the macOS firewall drops inbound
connections to the Python app bundle before they reach the server. The board is
behaving correctly; the host is refusing it. CLAUDE.md carries the one-line fix.

Version 0.2.1 (2026-08-23)
---------------------------
Post-release hardening on phase v0.2. The end-of-phase sweep over the v0.1 and
v0.2 code reviews found one still-unfixed MEDIUM finding.

- orchestrator: the conversation window is bounded at 40 messages, trimmed from
  the front. Session history grew by two messages per turn with no cap and the
  whole of it was resent to the model every turn, so a long-lived connection cost
  more per turn than the last one did and would eventually meet the context limit
  as an unexplainable llm_failed.

  The v0.2 review had deferred this to v4.2, reasoning that a window here would
  pre-empt that phase's design. The sweep found that reasoning half wrong:
  ARCHITECTURE already specifies the number -- the rolling 40-message window --
  and what belongs to v4.2 is the persistence, not the bound. ARCHITECTURE now
  says so explicitly, so v4.2 adds SQLite behind an existing window.

No contract changed. 333 tests passing.

Version 0.2.0 (2026-08-23)
---------------------------
Roadmap phase v0.2 -- Gemini and the orchestrator. The echo becomes a
conversation: a real answer from the model, streamed.

- providers: the LLMProvider seam, with the streaming guarantee written into the
  type -- stream() returns an async iterator and is not itself a coroutine
  function, so the first delta can be awaited under its own budget rather than
  the whole call. A deterministic mock ships with it and is what every test uses.
- providers/gemini: Gemini 2.5 Flash with thinkingBudget 0, the documented reason
  the model was chosen. Deltas are forwarded as they arrive; safety settings are
  explicit rather than inherited; every vendor exception is translated, so the
  orchestrator never sees a google.genai type.
- orchestrator: runs a turn and streams it. Each delta leaves as its own reply
  frame the moment it exists -- the reply is never accumulated and sent whole.
  The first-token budget (~8 s) is awaited on the first delta only, so a stalled
  model fails fast while a slow-but-flowing one is never cut off mid-reply.
  Per-session history, in memory.
- prompt: a minimal system prompt -- a placeholder character until v4.1,
  Ukrainian, and the brevity rule that matters for a character who is heard
  rather than read.
- protocol: ErrorCode gains a twelfth value, bad_frame. It and internal split by
  whose fault it is -- the device sent something unparseable, versus the server
  broke. From v0.4 the device renders the error face for whatever code arrives,
  so the attribution decides which side a person is shown as being at fault.
- router: the Responder seam is now a stream of deltas, and a turn's reply is
  many frames closed by one final frame. A turn that fails sends an enumerated
  error and no terminal reply, and the connection stays open.
- config: the three Gemini variables. Loading never needs a key; only selecting
  the real provider does, so the suite runs on a machine with none and a server
  about to hold a conversation fails at startup rather than on its first turn.
- tests: 327 passing, no paid call. The streaming property is asserted by
  interleaving rather than by counting frames, and was verified against a
  deliberately buffering implementation. One live test exists, guarded twice.

Code review of the phase fixed four findings: the API key no longer renders in
repr(Settings); a bug in a responder now produces an error frame instead of
dropping the device; provider status codes no longer tell the device the server
is unreachable when it is Gemini that is down; and a turn now always either
completes or rolls back, with no third ending.

Deferred to v4.2: session history is unbounded and resent whole every turn. The
rolling 40-message window is that phase's specified design and writing a lesser
one here would pre-empt it.

Version 0.1.0 (2026-08-23)
---------------------------
Roadmap phase v0.1 -- Server skeleton and the wire contract. The first release:
a server exists, a fake device can talk to it, and the wire format is pinned.

- protocol: the WS device<->server seam as a pure module -- the full message
  vocabulary in both directions, the eleven-value ErrorCode enum, the five
  capability flags, PROTO_VERSION 1 with no compatibility window, the
  PCM16/16 kHz/mono constants, hello negotiation, and the rule that binary
  frames carry raw payloads with no envelope. Pinned by a contract test.
- router: one connection state machine per device -- awaiting_hello -> ready ->
  closing, ping/pong, clean teardown on every path. text_in is answered through
  an injected Responder, which echoes in v0.1 and becomes the orchestrator in
  v0.2.
- app: the FastAPI application and its /ws endpoint, with the WebSocket adapter
  that keeps the router framework-free.
- config: ROBOFACE_WS_HOST, ROBOFACE_WS_PORT and ROBOFACE_LOG_LEVEL, read from
  the environment and server/.env, with both sources injectable for tests.
- logging: one JSON object per line, keyed by device_id and session_id bound
  once per connection. Bodies are never logged -- a length is.
- tests: a reusable fake device that speaks the protocol, plus unit, contract
  and integration suites. 174 passing, no paid API call, no hardware.
- CI: ruff, strict mypy and pytest on every push and pull request.

Code review of the phase fixed four findings: inbound text frames are now capped
at 64 KiB and refused before parsing; a log field can no longer overwrite the
device_id or session_id it claims to describe; an unrecognised log level falls
back instead of raising out of the router and dropping a live connection; and a
stalled server now fails the suite instead of hanging it.

Known open question, deliberately not decided here: ErrorCode has no value
meaning "the device sent something this server cannot parse", so a malformed
frame is reported as `internal`. See specification/roadmap/implementation/
v0.1-code-review.md, finding 9.
