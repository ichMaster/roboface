RoboFace -- release notes
=========================

Version 0.4.1 (2026-08-24)
---------------------------
Post-release fixes on phase v0.4. The server moved off the development Mac, which
cannot host it, onto a Linux box on the same LAN. The board now reaches it and a
text turn completes end to end: typed at the board, answered by Gemini, rendered
as a state on the panel.

- The Mac cannot serve the board, and this is not a bug in the firmware. Its
  endpoint filtering accepts an inbound LAN connection and then destroys the
  socket before the application's first read (errno 57, ENOTCONN). It is a
  socket-layer filter, which is why it was so hard to see: the TCP handshake
  completes, so `nc -z` calls the port open and only the first read fails. Not the
  Application Firewall's per-app allowlist -- an explicitly allowed binary fails
  identically -- and not the router, which needs no changes at all.
- tools/remote.sh: deploy and administer the server on a remote box over plain
  SSH -- deploy, start, stop, restart, status, health, logs, ping, shell. No
  systemd and no sudo; start/stop is a PID file and a log file. `health` asks its
  two questions from the workstation, because a listener the board cannot reach is
  not a running service.
- DEPLOYMENT.md: the server's lifecycle, the same operations written out in plain
  ssh for a machine with no checkout, and the firmware's build/flash/config half.
- tools/board.py never read stdin, so every line typed at it was discarded; only
  --send worked. It is two-way now. Transient CDC read failures after a write are
  absorbed rather than treated as a disconnect -- reattaching threw away exactly
  the output that mattered, the reply to the command just sent. The drop message
  no longer claims the board reset, which the uptime counter disproves.
- server/.env is no longer sourced into the shell anywhere. It was redundant --
  load_settings() reads the file itself, by a path derived from config.py's own
  location -- and lossy: WEATHER_URL's value contains an unquoted `&`, so the
  shell backgrounds there and the assignment never arrives. Exit code 0, no
  message. As _resolve() reads the environment before the file, a mangled value
  would have overridden the correct one rather than merely going missing.
- chat.py and firmware/src/config.example.h point at the server box. The firmware
  needs a literal address: it links no mDNS resolver, so the .local name the
  host-side tools could use would never resolve there.
- TESTING.md 5 rewritten. It had described the link as an unresolved blocker and
  suggested a tunnel that cannot work -- the firmware speaks ws:// only -- and its
  account of the failure named the wrong mechanism.

Version 0.4.0 (2026-08-24)
---------------------------
Roadmap phase v0.4 -- Face stub and the renderer interface. **Phase v0 is
complete**: a server, a wire, a board, and a face.

The screen now says something, and it never says it in words. A device state is
an expression; the only text this firmware puts on a panel is an enumerated error
code, which is an identifier rather than a state.

- pure/face.h: the state -> face recipe table. Five normalised numbers per state,
  no colours and no pixels, so v2's five skins can share one expression grammar.
  Total over all eight states including listening, which v1 drives -- a table
  covering only the reachable ones would have failed on the screen. Every pair of
  the six DoD faces is provably distinct, with headroom, so a later tweak cannot
  silently make two of them alike.
- pure/chrome.h: what is visible and when it fades. The rules are almost entirely
  about time, so they live where a fake clock proves the three-second settle in
  microseconds. "A fault never auto-dismisses" is implemented as an omission and
  tested by advancing an hour; that omission is what makes the fading safe for
  everything else.
- pure/layout.h: the screen geometry. "Never block the face" is a property of the
  numbers, so a host test proves the bands cannot overlap -- including the
  negative case, without which every other assertion would be vacuous.
- IFaceRenderer (begin/show/setAudioLevel/tick), fixed now while the renderer
  behind it is a stub. That is the point of a stub: v2 implements this interface
  rather than inventing one. setAudioLevel exists and does nothing until v1.
- StubRenderer: a full-screen sprite in PSRAM, drawn into and pushed whole, which
  is why "no tearing" is true rather than hoped.
- Chrome on screen: the status cluster and the fault line, in the outer 28 px
  bands, with the overlap rule enforced by static_assert in the module that could
  violate it.
- A /faces self-test that cycles the six states, announcing each on serial while
  the screen shows only the face -- which is how a person checks a screen that
  deliberately never says what it is showing.

main.cpp no longer draws: the DoD's "the renderer interface is the only way the
app draws a face" is now true and checkable by grep, where before it was false.

Three bugs, each caught somewhere different: the chrome view drew invented facts
(caught in review before the commit); the self-test claimed "back to the real
state" and left the device in error (caught by reading the serial output of a
real run); and main.cpp's direct drawing (caught by the reconciliation step,
before any code was written).

Code review fixed two more, both the same defect in two forms -- the loop doing
expensive work at 200 Hz for facts that change at 8 Hz or slower: the whole
153 KB sprite pushed every iteration, implying 30 MB/s on a bus that carries
about 5, and the AXP2101 polled ~400 times a second for a battery percentage that
moves on the scale of minutes.

Definition of Done: met, including the clause only a person can judge -- six
visibly distinct faces switching cleanly with no tearing, confirmed on the board.

Still outstanding from v0.3, and not this version's to fix: the firmware-to-server
turn is unverified because this development machine's managed policy refuses
inbound LAN connections to the server process.

Version 0.3.0 (2026-08-24)
---------------------------
Roadmap phase v0.3 -- Firmware skeleton: Core S3 as a WSS client. The first C++
in this repository, and the first code that runs on the hardware.

- firmware/: a PlatformIO project with two environments, and the split between
  them is the architecture. `native` compiles only src/pure/ -- header-only,
  Arduino-free -- so an #include <M5Unified.h> reaching pure code fails the host
  build. 64 host tests now run on a laptop with no board attached.
- pure/ws_protocol.h: the device half of the WS protocol seam, mirrored from the
  released protocol.py. Both vocabularies, all twelve error codes including
  bad_frame, proto_ver 1, pcm16/16000/1, the frame cap. A declared-but-unhandled
  type parses as unsupported rather than malformed, and an unrecognised error code
  still parses -- a device that cannot parse an error cannot report one.
- pure/state.h: the specified state machine, with a transition function that is
  total over (state, event). pure/backoff.h: exponential, capped, jittered.
  pure/line_reader.h: bounded, CRLF-aware. pure/ws_url.h: the SERVER_URL parser.
- app/net.cpp and app/ws.cpp: WiFi bring-up with a reconnect supervisor, and the
  WebSocket client. Glue owns the hardware and decides nothing; every schedule
  comes from the tested pure half.
- main.cpp: the serial debug channel. A typed line becomes a text_in and reply
  deltas print as they arrive, inside the receive path -- a buffered version would
  satisfy the wording and lose the property v0.2 exists to provide.
- tests/contract/test_firmware_mirror.py: reads the C++ header and compares it to
  protocol.py in the Python CI job, so a drift between the two languages is caught
  by someone who never runs pio.

The transport is ws://, not wss://. The server runs uvicorn with no TLS, so
ARCHITECTURE now records the gap rather than promising a transport the product
does not offer. Closing it is one line in config.h plus a certificate.

Four bugs were found by the tests and the hardware: a state machine that claimed
`idle` while unable to reach the server; two build environments compiling the same
headers under different C++ standards; a URL parser accepting port 0 and 70000;
and `Serial` writing to the UART pins instead of USB, which made the debug channel
-- this version's only turn source -- silent while the board ran perfectly.

Code review fixed three more: the first connection attempt was aborted and
restarted microseconds later, the reconnect log described a delay it never waited,
and the device had inherited the server's 64 KiB frame cap, which is a fifth of
this board's RAM.

Definition of Done: `pio test -e native` passes and `pio run -e cores3` compiles
clean. On hardware, the board joins WiFi, parses its server URL, holds
`wifi_connecting` correctly and backs off with jitter exactly as the host tests
predict. The end-to-end turn is NOT yet verified: the macOS firewall drops inbound
connections to the Python app bundle before they reach the server. The board is
behaving correctly; the host is refusing it. CLAUDE.md carries the one-line fix.

Version 0.2.1 (2026-08-23)
---------------------------
Post-release hardening on phase v0.2. The end-of-phase sweep over the v0.1 and
v0.2 code reviews found one still-unfixed MEDIUM finding.

- orchestrator: the conversation window is bounded at 40 messages, trimmed from
  the front. Session history grew by two messages per turn with no cap and the
  whole of it was resent to the model every turn, so a long-lived connection cost
  more per turn than the last one did and would eventually meet the context limit
  as an unexplainable llm_failed.

  The v0.2 review had deferred this to v4.2, reasoning that a window here would
  pre-empt that phase's design. The sweep found that reasoning half wrong:
  ARCHITECTURE already specifies the number -- the rolling 40-message window --
  and what belongs to v4.2 is the persistence, not the bound. ARCHITECTURE now
  says so explicitly, so v4.2 adds SQLite behind an existing window.

No contract changed. 333 tests passing.

Version 0.2.0 (2026-08-23)
---------------------------
Roadmap phase v0.2 -- Gemini and the orchestrator. The echo becomes a
conversation: a real answer from the model, streamed.

- providers: the LLMProvider seam, with the streaming guarantee written into the
  type -- stream() returns an async iterator and is not itself a coroutine
  function, so the first delta can be awaited under its own budget rather than
  the whole call. A deterministic mock ships with it and is what every test uses.
- providers/gemini: Gemini 2.5 Flash with thinkingBudget 0, the documented reason
  the model was chosen. Deltas are forwarded as they arrive; safety settings are
  explicit rather than inherited; every vendor exception is translated, so the
  orchestrator never sees a google.genai type.
- orchestrator: runs a turn and streams it. Each delta leaves as its own reply
  frame the moment it exists -- the reply is never accumulated and sent whole.
  The first-token budget (~8 s) is awaited on the first delta only, so a stalled
  model fails fast while a slow-but-flowing one is never cut off mid-reply.
  Per-session history, in memory.
- prompt: a minimal system prompt -- a placeholder character until v4.1,
  Ukrainian, and the brevity rule that matters for a character who is heard
  rather than read.
- protocol: ErrorCode gains a twelfth value, bad_frame. It and internal split by
  whose fault it is -- the device sent something unparseable, versus the server
  broke. From v0.4 the device renders the error face for whatever code arrives,
  so the attribution decides which side a person is shown as being at fault.
- router: the Responder seam is now a stream of deltas, and a turn's reply is
  many frames closed by one final frame. A turn that fails sends an enumerated
  error and no terminal reply, and the connection stays open.
- config: the three Gemini variables. Loading never needs a key; only selecting
  the real provider does, so the suite runs on a machine with none and a server
  about to hold a conversation fails at startup rather than on its first turn.
- tests: 327 passing, no paid call. The streaming property is asserted by
  interleaving rather than by counting frames, and was verified against a
  deliberately buffering implementation. One live test exists, guarded twice.

Code review of the phase fixed four findings: the API key no longer renders in
repr(Settings); a bug in a responder now produces an error frame instead of
dropping the device; provider status codes no longer tell the device the server
is unreachable when it is Gemini that is down; and a turn now always either
completes or rolls back, with no third ending.

Deferred to v4.2: session history is unbounded and resent whole every turn. The
rolling 40-message window is that phase's specified design and writing a lesser
one here would pre-empt it.

Version 0.1.0 (2026-08-23)
---------------------------
Roadmap phase v0.1 -- Server skeleton and the wire contract. The first release:
a server exists, a fake device can talk to it, and the wire format is pinned.

- protocol: the WS device<->server seam as a pure module -- the full message
  vocabulary in both directions, the eleven-value ErrorCode enum, the five
  capability flags, PROTO_VERSION 1 with no compatibility window, the
  PCM16/16 kHz/mono constants, hello negotiation, and the rule that binary
  frames carry raw payloads with no envelope. Pinned by a contract test.
- router: one connection state machine per device -- awaiting_hello -> ready ->
  closing, ping/pong, clean teardown on every path. text_in is answered through
  an injected Responder, which echoes in v0.1 and becomes the orchestrator in
  v0.2.
- app: the FastAPI application and its /ws endpoint, with the WebSocket adapter
  that keeps the router framework-free.
- config: ROBOFACE_WS_HOST, ROBOFACE_WS_PORT and ROBOFACE_LOG_LEVEL, read from
  the environment and server/.env, with both sources injectable for tests.
- logging: one JSON object per line, keyed by device_id and session_id bound
  once per connection. Bodies are never logged -- a length is.
- tests: a reusable fake device that speaks the protocol, plus unit, contract
  and integration suites. 174 passing, no paid API call, no hardware.
- CI: ruff, strict mypy and pytest on every push and pull request.

Code review of the phase fixed four findings: inbound text frames are now capped
at 64 KiB and refused before parsing; a log field can no longer overwrite the
device_id or session_id it claims to describe; an unrecognised log level falls
back instead of raising out of the router and dropping a live connection; and a
stalled server now fails the suite instead of hanging it.

Known open question, deliberately not decided here: ErrorCode has no value
meaning "the device sent something this server cannot parse", so a malformed
frame is reported as `internal`. See specification/roadmap/implementation/
v0.1-code-review.md, finding 9.
